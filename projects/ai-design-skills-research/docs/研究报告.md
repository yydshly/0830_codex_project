# `ai-design-skills` 源码与能力研究报告

研究日期：2026-08-31  
研究对象：[`elayadesign/ai-design-skills`](https://github.com/elayadesign/ai-design-skills)  
固定提交：`1c1e97cb9878e236552c772092dda7adcdddbcb2`

## 1. 结论先行

这个库当前提供的不是可直接运行的网页效果，而是一个名为 `landing-page-design` 的知识型 Skill。它通过 Markdown 规则改变 AI 编码代理的决策过程：先确定用户、Offer 和转化动作，再组织页面结构和文案，最后用一套封闭视觉规则生成或修改网页代码。

因此需要区分三层：

| 层 | 谁负责 | 当前仓库是否提供 |
| --- | --- | --- |
| 设计方法 | 需求采集、信息结构、转化原则、视觉规则 | 提供 |
| 网页实现 | HTML、CSS、React、Tailwind、Framer Motion 等代码 | 不提供，由编码代理临时生成 |
| 运行与验证 | 浏览器渲染、截图、无障碍、性能、转化实验 | 不提供 |

它的直接价值是减少代理的随意发挥和常见遗漏；更大的价值是展示如何把设计师的经验与偏好写成 AI 可重复执行的工作规程。它不是新的模型能力，也没有给代理增加新的外部工具权限。

### 1.1 最终复盘：对当前强模型的增量价值有限

经过源码分析、受控对照和实际场景实现，本研究形成进一步结论：当前强模型已经掌握常见落地页结构、CSS、响应式、动效和状态实现。用户直接描述“浮动导航、全屏玻璃菜单、逐词滚动、审核状态和移动端回退”，模型不依赖此仓库也能完成。因此，不能把演示页面中由模型编写的效果归因于仓库提供了新的前端能力。

本仓库更准确的定位是：

```text
通用落地页提示词 / SOP
+ 作者个人视觉偏好
+ 状态与发布检查清单
= 对模型输出的基础约束
```

它在能力较弱、上下文不足或团队需要统一输出时仍有提醒价值，但对当前强模型的能力上限提升很小。若研究目标是高级 UI 效果、独有组件、WebGL/Shader、动效编排或模型原本不会的技术，本仓库没有继续深挖的必要。值得保留的是 `SKILL.md` 的经验封装形式，而不是把其中的普通网页规则当作技术壁垒。

## 2. 当前仓库实际包含什么

固定提交的工作树只有 `README.md`、`LICENSE`、`.gitignore` 和一个 [`SKILL.md`](../upstream/skills/landing-page-design/SKILL.md)。没有：

- React、Vue 或 HTML 页面；
- CSS、GSAP、Framer Motion 或 Three.js 效果代码；
- 组件模板、图片、图标或设计稿；
- 可执行脚本、MCP 服务或外部 API；
- 单元测试、浏览器测试、性能测试或转化实验；
- 多品牌配置或多个已完成的设计 Skill。

所以仓库名字中的 `skills` 是未来集合定位，而不是当前能力数量。当前核心文件为 403 行，分为两大部分：

1. Part A：策略与页面结构；
2. Part B：视觉系统与交付检查。

## 3. 能力描述

### 3.1 需求采集与转化目标

Skill 要求代理在设计前收集：

- 唯一主要动作：试用、预约、购买、候补或下载；
- Offer 的具体内容与转化定义；
- ICP、用户问题、前三项转化异议；
- 流量来源以及访客已有认知；
- Logo、评价、数字、案例和产品截图；
- 品牌语气、设计方向与移动端优先级。

如果用户无法回答，代理可以明确写出假设后继续，不因信息不完整无限停顿。

### 3.2 页面结构与布局决策

Skill 把落地页组织成三段论证：

```text
首屏：价值主张 + CTA + 初步证明 + Hero 视觉
中段：问题到方案 + 收益 + 使用步骤 + 社会证明
尾段：FAQ + 风险逆转 + 最终 CTA
```

同时定义四类布局：经典分节、长篇叙事、极简转化和对比页。代理必须选择一种并说明原因，而不是只根据语言模型习惯生成相同的三栏卡片页面。

### 3.3 转化文案

规则强调一个页面只有一个主要动作，功能要改写为用户收益，证明应放在主张附近，并通过试用、退款或随时取消等方式降低风险。输出顺序要求代理先给出页面大纲、Hero 文案、收益、三步流程、FAQ、SEO 建议和布局选择，再开始写代码。

### 3.4 SEO 与 AEO

它区分广告短期页与常青搜索页：前者建议 `noindex`，后者补充标题、描述、内部链接和问答结构，并在适合时增加 FAQ schema。这部分是指导原则，不包含自动生成或验证结构化数据的程序。

### 3.5 强约束视觉系统

Part B 对视觉值进行封闭选择：

- 字体仅推荐 Geist、Manrope、Geist Mono、Poppins；
- 字号对齐 Tailwind 默认阶梯；
- 间距只能从 0、2、4、8、12、16、24、32、40、48、64、80、96px 中选择；
- 嵌套圆角使用 `inner radius = outer radius - gap`；
- 深色背景限制为六个颜色；
- Hero 文案宽度限制为 680px；
- 图标限制为 Phosphor、Solar、Iconamoon；
- 动效使用指定 cubic-bezier，并偏好 `IntersectionObserver`；
- 每个页面强制存在逐词点亮的 tagline reveal 区块。

这些规则能显著提高同一代理多次生成时的视觉一致性，但它们主要代表作者审美，不是跨品牌的普遍真理。

### 3.6 内容、状态与发布完整性

Skill 要求避免 Lorem Ipsum、常见 AI 套话和失真的占位品牌，并要求补齐 Hover、Active、Focus、Loading、Empty、Error。交付检查还覆盖法律链接、404、表单校验、跳到正文、favicon、社交 meta、alt 文本和语义化 HTML。

这是它相对普通“做一个漂亮网页”提示词更有价值的部分：它把容易遗漏的完成度要求放进统一清单。

## 4. 工作原理

### 4.1 Skill 发现

`SKILL.md` 顶部 YAML 包含 `name` 和 `description`。支持原生 Skill 的代理可以先读取这两项元数据，在用户请求落地页、营销网站、组件或设计审查时判断是否加载全文。

如果宿主不支持 Skill 发现，README 建议将全文复制进 `AGENTS.md`、`.windsurfrules`、`.clinerules` 或系统提示词。此时它退化为始终存在的项目规则，而不是按需加载的模块。

### 4.2 上下文条件化

代理读取全文后，这些规则进入当前推理上下文。模型没有被重新训练，也没有安装新的渲染引擎；它只是生成代码时受到更多领域指令约束。

可以把它理解为：

```text
通用编码代理
+ 落地页领域知识
+ 工作步骤
+ 禁止项与设计 Token
+ 输出格式与验收清单
= 更像特定设计师工作的编码代理
```

### 4.3 降低生成自由度

普通提示词只说“做得高级”，模型可以自由选择字体、尺寸、间距和结构，输出方差很大。这个 Skill 通过封闭 Token、固定决策表和禁止项缩小搜索空间，从而提高一致性和可预测性。

### 4.4 先策略、后视觉

Part A 必须先于 Part B。这个顺序避免代理先制作漂亮 Hero，再寻找与画面匹配的产品逻辑。页面结构先承担转化论证，视觉系统随后承担层级、品牌感和交互反馈。

### 4.5 输出契约与自检

固定输出顺序迫使代理显式暴露自己的信息架构和文案选择；分节实现减小每次修改的范围；末尾 checklist 让代理在交付前重新检查常见遗漏。

这仍然是概率性约束。没有自动检查器时，代理可能漏掉或错误理解规则；用户显式要求又被规定为高于 Skill，因此相同 Skill 在不同任务中的遵守程度仍会变化。

## 5. 使用场景

### 5.1 最适合

- SaaS、AI 产品、开发者工具和 App 的新落地页；
- 试用、预约 Demo、下载、候补名单等单目标页面；
- 广告、邮件和社交流量对应的活动页；
- 创业 MVP 缺少专职设计师时的初始设计基线；
- 用 Codex、Claude Code、Cursor 快速生成营销页原型；
- 审查 AI 生成页面是否缺少内容、状态和发布细节。

### 5.2 有条件适合

- 已有品牌系统：只保留流程，替换整个视觉值部分；
- 后台或 Dashboard：可借用状态和 Token 规则，但不应套用单一转化叙事；
- 中文页面：可借用结构，必须重写英文断词、文案和字体规则；
- 现有网站升级：作者另有 `redesign-existing-projects`，本 Skill 更偏向从零构建。

### 5.3 不宜直接套用

- 电商、媒体、社区和门户等多目标首页；
- 已有严格 Design Token 与组件库的大型产品；
- 医疗、金融、政府等强合规界面；
- 追求极低动效或对低端移动设备性能高度敏感的项目；
- Figma 像素级还原、复杂 WebGL、游戏 HUD 等非营销页面；
- 需要真实证明“提升转化率”的商业决策。

## 6. 优点

1. 从 Offer、受众和 CTA 出发，而不是直接写样式。
2. 把结构、文案、视觉、状态和发布要求放进一条链路。
3. 封闭 Token 能减少 AI 随机造值和跨组件漂移。
4. 分节构建和固定输出格式便于用户审核与回滚。
5. 将空状态、错误状态、404、alt 和表单校验纳入完成定义。
6. 文件单一、MIT 许可，容易复制、修改和团队共享。

## 7. 局限与风险

### 7.1 “高转化”是方法主张，不是实验证据

仓库没有页面样例、埋点、A/B 测试或转化数据。它包含常见 CRO 原则，但不能据此证明使用后一定提高转化率。

### 7.2 视觉规则过度泛化

禁止 Inter、Roboto、Arial、背景渐变、斜体和 Material Icons 都是风格选择。`description` 却要求在任何 Web UI 中都应用，会与真实品牌系统和产品语境冲突。

### 7.3 “更像真的假数字”有诚信风险

规则禁止 `50%` 等整数字，转而建议 `47.2%` 等“自然数字”。如果数据并非真实测量，这会让虚构证明更具有欺骗性。安全扩展应改为：只使用有来源的真实数据；演示数据必须显式标记为示例；没有证明时保留待补占位，而不是制造可信细节。

### 7.4 动效与性能、无障碍并未闭环

规则强制元素入场动画和逐词点亮，示例使用 `transition-all`、模糊与 800ms 以上时长，却没有要求 `prefers-reduced-motion`、低端设备降级或动画属性白名单。按钮 padding 也不自动保证 44×44px 触摸目标。

### 7.5 规则之间存在轻微冲突

B7 表述为永远不要使用 `window.addEventListener('scroll')`，B11 又允许经过 `requestAnimationFrame` 节流的单个 scroll listener。预期可以解释，但对代理而言应写成更精确的统一规则。

### 7.6 缺少确定性验证

没有 linter、schema、测试或浏览器检查器去证明生成结果符合规则。Checklist 只能提醒模型，不能像程序测试一样阻止违规交付。

### 7.7 技术栈隐含偏向 Tailwind

字号、圆角和代码示例大量依赖 Tailwind 类名。CSS Modules、原生 CSS、Design Tokens 或其他框架需要额外翻译层。

## 8. 可扩展方向

### 第一层：先把规则变得可信、可配置

1. **品牌 Profile**：将字体、颜色、圆角、间距、图标和动效抽到独立配置，Skill 只描述选择方法。
2. **真实性规则**：禁止虚构评价、Logo、统计和案例；为示例数据增加明确标签。
3. **中文与国际化**：增加中文字体、CJK 换行、中英混排、RTL、文案长度和多语言布局规范。
4. **无障碍与低动效**：加入对比度、键盘顺序、触摸目标、`prefers-reduced-motion` 和非动画等价体验。
5. **明确适用范围**：将落地页、Dashboard、电商和内容网站拆成不同 Skill，避免一套规则覆盖所有 UI。

### 第二层：从知识型 Skill 升级为工程型 Skill

1. **Token 检查器**：扫描任意字号、任意间距、非法颜色和圆角。
2. **内容检查器**：检测 Lorem Ipsum、AI 套话、无来源数字、空链接和重复头像。
3. **SEO/AEO 检查器**：验证 title、description、canonical、Open Graph、robots 和结构化数据。
4. **无障碍检查器**：接入 axe，验证标签、焦点、对比度和键盘操作。
5. **浏览器验收**：用 Playwright 截取手机、平板、桌面截图，检测溢出、死链和交互状态。
6. **性能门禁**：限制模糊、动画数量、字体体积和首屏资源，运行 Lighthouse 或 Web Vitals 检查。

脚本输出可以给出可重复的 PASS/FAIL，这比让模型自行声称“已符合”可靠得多。

### 第三层：形成可复用网页生产系统

1. 提供 React、Next.js、Vue、原生 HTML 等框架适配器；
2. 提供经过验证的 Hero、FAQ、Proof、Pricing、Form 组件模板；
3. 连接 Figma Variables、Style Dictionary 或项目 Design Token；
4. 连接图片生成和资产审批流程，但保留来源和版权记录；
5. 生成分析事件、漏斗定义和实验假设；
6. 用同一 Brief 生成多个可比较变体，并支持 A/B 测试；
7. 保存页面决策清单和验证结果，形成可追溯的发布 Manifest。

### 第四层：优化 Skill 自身架构

当前 403 行全文同时包含策略、文案、视觉和 QA。可以按渐进加载拆成：

```text
landing-page-design/
├── SKILL.md                 # 触发条件、总流程与路由
├── references/
│   ├── strategy.md          # ICP、Offer、异议、结构
│   ├── copywriting.md       # 文案与中文本地化
│   ├── visual-system.md     # 品牌 Token 与组件规则
│   ├── motion-a11y.md       # 动效、性能和 reduced motion
│   └── seo-release.md       # SEO、AEO 和发布清单
├── profiles/
│   ├── default.json
│   └── project-brand.json
└── scripts/
    ├── lint-design-tokens.*
    ├── audit-content.*
    └── verify-page.*
```

主 Skill 只加载当前任务需要的参考文件，脚本负责确定性检查，品牌值不再硬编码在通用工作流中。

## 9. 对本工作区和使用者的意义

如果目标是用 Codex 实现产品、游戏或 AI 工具的发布页，这个库可以作为页面策略和完成度基线，减少“画面漂亮但说不清产品”“只有首屏没有交付细节”等问题。

但更重要的意义是 Skill 工程方法：

```text
收集必要输入
→ 给出决策表
→ 规定执行顺序
→ 收紧可选值
→ 明确输出契约
→ 用检查器验证
```

这套结构不仅适用于落地页，也可以迁移到游戏关卡、视觉资产、视频生产、代码审查和发布流程。真正应该长期积累的是个人或团队自己的判断规则、验证工具和案例，而不是永久采用作者选择的字体与动效。

## 10. 推荐采用方式

不建议直接把原始全文设为所有项目的全局规则。推荐顺序是：

1. 保留 Part A 的需求、结构与输出流程；
2. 将 Part B 改成当前项目的品牌 Token；
3. 删除强制逐词动画等不适用于所有页面的规则；
4. 加入真实性、中文、无障碍和性能规则；
5. 为关键规则编写自动检查脚本；
6. 用同一 Brief 做三组对照页面并真实验收。

最终定位应是“设计决策与网页验收系统”，而不只是“让 AI 生成得更好看的一段长提示词”。

## 11. 可选验证方案（不作为当前继续方向）

如果未来需要定量研究“外部规则是否能提高弱模型或团队输出一致性”，可以选择一个真实产品 Brief，建立三组页面：

| 组别 | 条件 | 要回答的问题 |
| --- | --- | --- |
| A | 不加载 Skill | 通用代理默认会遗漏什么 |
| B | 加载原版 Skill | 一致性和完整度是否提高，风格是否模板化 |
| C | 加载增强版 Skill | 品牌、中文、性能、真实性和无障碍是否同时改善 |

统一采集响应式截图、axe、Lighthouse、死链、Token 合规、任务完成率和人工盲评。这只用于验证约束的一致性收益，不应被解释为仓库提供了新的网页实现能力。当前研究建议结项，把后续投入转向可复用视觉资产、高级动效模块、私有设计系统和自动浏览器优化闭环。
