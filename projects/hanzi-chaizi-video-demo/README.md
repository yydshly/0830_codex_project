# 汉字拆字视频能力演示

展示网页：<https://yydshly.github.io/0830_codex_project/demos/hanzi-chaizi-video-demo/>

## 研究问题

[`Mr-funny/hbg-hanzi-chaizi-video`](https://github.com/Mr-funny/hbg-hanzi-chaizi-video) 是否已经具备“输入任意汉字即可生成逐笔拆字短视频”的能力？它现在适合哪些场景，成为可规模化产品还缺什么？

## 背景与假设

- 已知背景：上游使用 Remotion、`hanzi-writer-data` 和 Edge TTS 制作“懒”字 9:16 样片。
- 核心假设：仓库能从源码稳定复现逐笔写字、部件拆分、旁白、字幕和 MP4 成片，但换字仍依赖人工改代码。
- 成功标准：从固定提交复现“懒”字；用“忙”验证迁移；用效果实验室验证扩展；用共享 JSON 驱动工作台样片；把“姓名祝福”落实为可操作 MVP；再用朋友提供的婚礼主题完成三端个案；七条 H.264 成片均包含可验证的视频与音轨，其中六条为 1080×1920、婚礼大屏片为 1920×1080。
- 不在本次范围：把上游重构成通用生成器、调用付费服务、发布到社交平台或把趣味联想验证为历史字源。

## 结论

上游不是一个可直接调用的“按笔画写任意汉字 Skill”，而是一套**已经跑通完整视频链路的单字样片工程**：

```text
汉字与文案
→ hanzi-writer-data 笔画路径
→ 人工标记部件笔画
→ Edge TTS 旁白与词语边界
→ Remotion 逐帧合成
→ 1080×1920 MP4
```

本次已成功渲染七条真实视频：上游“懒”字 10.517 秒；“忙”字 12.779 秒；效果实验室 31.595 秒；配置驱动“明”字 8.555 秒；姓名祝福“沐阳”12.544 秒；“张帅 × 董小姐”婚礼竖版故事 20.000 秒；婚礼横版大屏片 25.000 秒。七者均为 H.264、30fps、AAC 48kHz 双声道；前六条为 1080×1920，横版片为 1920×1080。

第二条证明方法可迁移；第三条证明路径可复用于教学、材质、部件和字族；第四条证明内容参数可以配置化；第五条把底层能力组织成姓名祝福消费闭环；第六、七条进一步证明一份婚礼主题可以扩展为“互动分镜＋竖版成片＋横版大屏＋迎宾海报＋本地 RSVP”的项目交付。更准确的判断是：**笔画是底座，情绪叙事和多端交付才是婚礼产品价值；演示闭环已跑通，但还没有在线渲染、真实 RSVP 接收、支付、照片管理、批量任务和长尾姓名覆盖。**

## 方法

1. 获取上游 `main` 固定提交并保存不含嵌套 `.git` 的源码快照。
2. 在 Node 22.15、Python 3.10.11、FFmpeg 6.1.3 环境安装锁定依赖。
3. 执行上游 Edge TTS 脚本，生成 `zh-CN-YunjianNeural`、`rate=-20%` 的旁白、词语边界、字幕 JSON 和 10.464 秒音频时间轴。
4. 用 FFmpeg 合成低振幅 C4/E4/G4 占位背景音，避免使用上游未分发且授权不明的 BGM。
5. 运行 ESLint 和 TypeScript 检查，再由 Remotion 渲染 314 帧 H.264 视频。
6. 使用 ffprobe 检查视频和音轨参数，抽取 0.4、2.2、6.6、10.0 秒关键帧进行目视验证。
7. 独立建立 `demo/mang-video`，复用相同技术思路，重新配置“忙”的 6 笔、`忄＋亡 → 心＋亡`、四行文案、小晓女声和蓝纸课堂主题，渲染 382 帧成片。
8. 构建静态展示页，将实验对照、现有能力、缺失能力、使用场景、技术路线和产品方向分层呈现。
9. 制作 31.512 秒六段旁白，并将“永”“明”“清／情／晴／请”的真实路径组织成教学、材质、部件、字族、跟写概念和多输出概念六章节，渲染 946 帧效果实验片。
10. 把五个目录字、四类场景和三套模板放入共享 JSON，由网页工作台读取并即时预览，也由 `ConfigurableHanzi` Composition 读取并渲染“明”字样片。
11. 建立姓名祝福产品配置，使用“沐”“阳”13 笔真实路径、程序化星光、双字组合、祝福和署名渲染 375 帧样片；网页加入 2–4 字姓名、四场景、三风格的可操作 MVP。
12. 在真实浏览器检查 1440×900、768×1024、390×844、五视频互斥播放、两个表单主路径、目录和媒体回退、键盘操作与 reduced-motion。

### 我们的“忙”字补充演示

补充演示不是剪辑上游视频，而是在独立目录中重新实现并真实渲染。它把上游的黑板主题换成蓝色方格纸，把目标字换成“忙”，将前 3 笔人工标记为竖心旁，并表达为 `忄＋亡 → 心＋亡`。视频持续 12.779 秒，明确标注“趣味联想 · 不等于历史字源”。

| 直接复用的方法 | 仍然需要人工的工作 |
| --- | --- |
| 按笔画中心线长度分配书写时间 | 决定哪些笔画属于哪个部件 |
| SVG 中心线扫描与真实轮廓裁剪 | 配置目标完整字形、缩放、位置与拆分布局 |
| 音频真实时长决定 Remotion 总帧数 | 创作并审核趣味文案，标明事实边界 |
| 确定性逐帧渲染为 H.264＋AAC | 选择音色、字幕分行和视觉主题 |

这说明下一轮工程化不应继续复制 TSX 文件，而应先把右栏手工作业提取成有 Schema、校验和人工覆盖的结构化配置。

### 最小内容工作台

工作台把“下一步应做配置化”的产品建议落实成了一个可操作闭环。网页从 `web/data/hanzi-workbench.json` 读取 5 个目录字（忙、永、明、清、安）、4 类场景和 3 套模板；用户可以改标题、核心文案和强调色，观察即时预览，恢复目录默认值，并下载与 Remotion props 同构的 JSON。

`ConfigurableHanziVideo.tsx` 读取同一份目录，按所选汉字载入真实 `hanzi-writer-data` 路径，按 `componentCut` 分色，并应用场景、模板、标题、文案和强调色。本次以目录中的“明／展陈／深蓝”配置渲染了 8.555 秒真实 MP4，证明“换内容不再复制一个新 TSX”这一步已经成立。

| 已跑通 | 尚未声称完成 |
| --- | --- |
| 五个受支持汉字、四类场景、三套视觉 token | 输入任意 Unicode 汉字自动完成部件映射 |
| 表单即时预览、校验、重置和 JSON 下载 | 浏览器内直接执行 Remotion 或在线排队渲染 |
| 同一 Composition 读取配置并生成 H.264＋AAC 成片 | TTS 文案生成、字幕时间轴和内容审核自动化 |
| 目录读取失败时启用内置回退配置 | 账号、资产管理、版本、计费与批量任务 |

因此它是“内容工作台最小原型”，不是已经上线的自助出片 SaaS。静态网页负责配置；真实 MP4 仍需本地命令或未来的渲染服务。

### 姓名祝福产品 MVP

R7 将用户选定的“祝福名字的绚丽效果”从产品方向变成了可操作原型。网页读取 `web/data/name-blessing.json`，支持 2–4 个汉字、生日／婚礼／新生／开业四类场景、鎏金星河／水墨流光／烟火绮梦三套风格，以及祝福语、署名、纪念日期和高光色。用户输入会即时更新视觉预览，可重播、重置并导出制作配置。

真实样片不是网页录屏。`NameBlessingVideo.tsx` 分别载入“沐”和“阳”的 13 笔真实路径，按偏旁分色逐笔写出，再加入程序化星光、组合环、祝福文案和署名，渲染为 375 帧、12.544 秒、1,846,697 字节的 H.264＋AAC 竖屏视频。

| 已经落地 | 诚实边界 |
| --- | --- |
| 姓名、场景、风格、文案、日期与颜色的完整前端配置 | 网页对任意姓名使用字体预览，不伪装成真实路径动画 |
| “沐阳”双字真实逐笔、分色、组合与绚丽效果 | 真实逐笔渲染目前只覆盖已导入并校验的“沐、阳” |
| 输入校验、预览重播、重置、JSON 导出和媒体回退 | 没有在线渲染、账号、支付、照片上传、分享或订单系统 |
| 生日、婚礼、新生和品牌四类产品入口 | 正式商业交付仍需音乐／字体授权、隐私和批量任务能力 |

这个实验改变了产品判断：内容工作台仍是生产底座，但更容易被普通用户感知和付费的前台商品，是“把一个人的名字做成有仪式感、可赠送、可分享的视频”。

### 真实婚礼案例：张帅 × 董小姐

R8 使用用户提供的真实主题信息“张帅、董小姐、9 月 12 日、延安”，按当前临近婚期暂定完整日期为 `2026.09.12`。案例不补全董小姐的真实姓名，不添加未提供的照片、酒店或联系方式。共享配置位于 `web/data/wedding-zhangshuai-dong.json`，网页和 `WeddingStoryVideo.tsx` 读取同一份称谓、日期、地点、誓言、五幕分镜和三端交付信息。

创意不再停留在“两个名字逐笔出现”，而是形成五幕故事：延安序章 → 两姓入场 → 红线相遇 → 姓名成礼 → 祝福定格。网页可在 9:16 微信请帖与 16:9 婚礼大屏构图之间切换，支持逐幕查看、自动播放、暂停、重播和 JSON 导出；真实样片则使用“张／董”的笔画数据，渲染为 600 帧、20.000 秒、2,582,303 字节的 H.264＋AAC 竖屏视频。

| 已经落地 | 继续生产前需要补充 |
| --- | --- |
| 张帅、董小姐、2026.09.12、延安和誓言的真实案例配置 | 确认年份、董小姐完整姓名及公开展示授权 |
| “张／董”真实逐笔、红线、同心圆、日期和祝福成片 | 新人照片、酒店屏幕尺寸、正式音乐与字体授权 |
| 9:16 请帖与 16:9 大屏互动构图，4:5 迎宾交付说明 | 分别渲染横版和迎宾成片，而不只停留在网页预览 |
| 配置失败回退、媒体错误恢复、键盘与 reduced-motion | 在线渲染、订单、支付、照片隐私与批量宾客回礼 |

红线和同心圆是婚礼视觉叙事，不被描述为汉字结构或历史字源；“帅／小姐”目前使用称谓排版，真实逐笔证据只覆盖已经导入并校验的“张／董”。

### 模拟完整婚礼交付包

R9 在用户明确授权“由我们模拟这些信息”后，补全了用于产品验证的非真实资料：模拟新娘全名“董雅宁”、11:58、延安 · 山河礼宴厅（演示场地）、替换地址、掩码联系电话、暖金／酒红着装色与三段演示故事。R10 又将原先的抽象人物占位替换为同一对完全虚构成年人的三张 AI 生成照片。配置中的 `simulation.status` 固定为 `DEMO_ONLY`，网页、横版成片和迎宾海报均持续显示“演示资料／AI 模拟照片／正式使用前请确认”，不把这些值混入用户提供的事实。

因此这不是一份可以直接用于朋友婚礼的最终物料，而是一套**可以逐项替换真实资料的产品级交互与媒体样板**。

### R10 完整素材探索

这次不是随机生成三张互不相干的“婚纱照”，而是先建立一张虚构身份锚点，再以参考图约束后续场景。三段生成意图依次是：延安风格秋日山谷初见；保持人物、服装和暖白／酒红色彩后并肩行走；继续保持身份并进入戒指约定的仪式高潮。三张图均由内置图像生成模式创建，没有使用真实新人照片或真人身份参考。

完整样例已经形成一条可检查的生产链：

1. `web/assets/wedding-ai/*.png` 保存三张 1122×1402 源图；同目录 720×900 WebP 用于网页和 Remotion。
2. `web/data/wedding-zhangshuai-dong.json` 统一描述三幕照片、替换说明和 `mediaPolicy`，网页、大屏与迎宾海报消费同一配置。
3. `web/assets/wedding-zhangshuai-dong-screen.mp4` 已重新渲染为照片版 25 秒横版成片；`web/assets/wedding-welcome-demo.png` 已重新渲染为照片版 4:5 海报。
4. `web/data/wedding-sample-delivery.json` 汇总请帖、大屏、迎宾和本地 RSVP 四项交付以及正式替换清单。

产品结论也因此更具体：笔画负责“姓名专属感”和开场识别，照片负责情绪与故事，多端适配、资料确认和现场保障负责把它变成可收费服务。AI 素材在这里用于探索视觉和提前确认方案，正式发布前仍必须替换为新人授权照片，或获得新人明确同意继续采用虚构视觉。

### 核心原理

1. `hanzi-writer-data` 为每一笔提供 `strokes` 轮廓和 `medians` 中心线。
2. 程序计算中心线长度，归一化为每一笔在总时间轴中的区间。
3. SVG `strokeDashoffset` 沿中心线推进，再通过真实笔画轮廓 `clipPath` 裁剪，产生书写效果。
4. “懒”的前 3 笔被人工标记为 `heart`，其余笔画标记为 `rely`；两组平移并与完整“心”“赖”交叉淡化。
5. Edge TTS 返回旁白与词语边界；Python 脚本把人工字幕行映射到边界，并用 ffprobe 读取真实音频长度。
6. Remotion 把音频时长乘以 30fps 得到总帧数，合成笔画、拆分、字幕、旁白和 BGM。

## 使用场景

### 当前最适合：汉字文化短视频栏目

现阶段最适合的不是完整儿童教育 App，而是“一字一条”的汉字文化短视频栏目。原因很直接：库本身已经能把一个汉字、四句文案、逐笔动画、趣味拆分、TTS、字幕和背景音组合成可直接发布的 9:16 MP4，不需要先补齐账号、课程、笔迹识别和学习记录。“忙”字 12.78 秒样片就是这个场景的第二次真实验证。

这是对底层技术适配度的判断；如果目标改为“普通用户最快感知价值并愿意分享或付费”，姓名祝福更有优势。它把笔画能力转化为个性化、情绪价值和纪念仪式，因此本次进一步选择它作为第一个消费产品 MVP。

儿童识字依然是重要的衍生方向，但要从“内容工具”进入“教育产品”，还需要课程体系、跟写纠错、年龄分级、复习机制和学习数据。这些不属于当前仓库已经证明的能力。

展示页新增“场景演示台”，每个场景都能切换输入、输出、待补能力和能力边界，并播放网页示例。文化短视频直接使用“忙”字完整成片；另外五个场景使用从效果实验室裁出的独立 H.264＋AAC 短片，因此在不支持视频时间点跳转的普通静态服务器上也能可靠播放对应证据。

真正可积累的壁垒不是几百行动画代码，而是高质量部件标注、可信来源链、文案审核体系、自动布局与 QA，以及发布后的内容效果数据。

## 对我们的意义

这个库对我们的价值，是验证了一条“汉字视觉内容生产链”，并证明它可以包装成有情绪价值的个性化商品，而不是直接给出一个儿童教育产品。较稳妥的产品路线是：

1. **前台首发：姓名祝福视频。** 先用生日、婚礼、新生和品牌纪念验证用户是否愿意完成配置、分享和付费；它是最容易感知的商品形态。
2. **生产底座：汉字视觉内容工作台。** 把姓名、模板、文案和渲染任务配置化，支撑个人单次订单与企业名单批量生产。
3. **中期资产：常用姓名字与模板库。** 为高频姓名字积累路径、偏旁分组、多字布局、授权音乐和视觉回归，形成质量壁垒。
4. **后续扩展：机构工具与动画 API。** 在稳定资产和真实需求上再进入课件、展陈、出版和互动教育，避免一开始承担完整平台复杂度。

当前仍不声称已完成自助 SaaS：没有在线渲染、账号权限、计费、订单、照片隐私、批量任务或长尾姓名质量。先用姓名祝福 MVP 验证“配置完成率、渲染成功率、分享率与付费率”，再决定服务化投入。

环境要求：Node.js 22、Python 3.10 或更高版本、FFmpeg/ffprobe。本次命令以 PowerShell 为例。

### 1. 安装依赖

```powershell
cd projects/hanzi-chaizi-video-demo/upstream
npm ci

cd ..
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r .\upstream\requirements.txt
```

### 2. 生成旁白

```powershell
cd upstream
..\.venv\Scripts\python.exe .\scripts\generate_lan_yunjian_edge_tts.py
```

### 3. 生成实验占位背景音

```powershell
ffmpeg -y -hide_banner -loglevel error `
  -f lavfi -i "sine=frequency=261.63:duration=10.6:sample_rate=48000" `
  -f lavfi -i "sine=frequency=329.63:duration=10.6:sample_rate=48000" `
  -f lavfi -i "sine=frequency=392.00:duration=10.6:sample_rate=48000" `
  -filter_complex "[0:a]volume=0.018[a0];[1:a]volume=0.012[a1];[2:a]volume=0.010[a2];[a0][a1][a2]amix=inputs=3:duration=longest,lowpass=f=1400,afade=t=in:st=0:d=1.0,afade=t=out:st=9.2:d=1.4[a]" `
  -map "[a]" -ac 2 -codec:a libmp3lame -q:a 4 `
  .\public\audio-lan-yunjian\background.mp3
```

### 4. 检查与渲染

```powershell
npm run lint
npm run render
```

上游默认输出为 `upstream/renders/lan-chaizi.mp4`。本研究展示使用的固定产物已复制为 `web/assets/hanzi-chaizi-demo.mp4`。

## 发现

### 已观察事实

- 上游只注册 `LanYunjianTransform` 一个 Composition，核心文件名、汉字数据、旁白和输出名均围绕“懒”硬编码。
- `kfcd/chaizi` 没有成为项目运行依赖；它用于人工核对结构，笔画分组仍在 TSX 中手工定义。
- 逐笔书写是真实路径动画；下方“变形”主要由部件平移、透明度切换和完整字形替换构成，并非通用 SVG 路径变形。
- 视频时长由实际旁白音频决定，字幕由人工语义分行和 Edge TTS 词语边界共同决定。
- 上游 CI 只执行 lint 与 TypeScript，没有媒体渲染、截图回归或音频质量检查。
- 我们的效果实验室已把真实路径复用于六类表现，但所有章节仍由 TSX 人工编排，不代表扩展已经插件化。
- 最小工作台已把 5 个受支持字和视觉/文案参数配置化；新增目录外汉字仍要补充数据导入和部件切分，并非任意输入自动出片。
- 姓名产品前端可以预览任意 2–4 个常用汉字；真实逐笔 Composition 当前只覆盖“沐、阳”，两者在页面中明确区分。
- 婚礼案例把“张／董”纳入真实笔画覆盖，并用同一 JSON 驱动网页五幕和 Remotion 成片；“帅／小姐”仍是称谓排版，不伪装成逐笔证据。
- 横版大屏 Composition 继续使用“张／董”真实路径；完整新娘姓名、时间、场地、地址、联系方式和故事全部属于 `DEMO_ONLY`；三张照片是 AI 生成的虚构成年人，页面和媒体中均有不可忽略的模拟标识。
- 本地 RSVP 只在当前 DOM 生成回执，刷新即消失；它验证的是表单和反馈体验，不代表已有后端接收或隐私存储能力。

### 推断

- 它的近期价值是可复用的 Remotion 竖屏样片和时间轴设计，而不是通用的汉字生成 API。
- 最先值得投入的是配置化和部件数据，而不是更多视觉特效；否则每增加一个汉字仍然会复制手工劳动。
- 若产品化，真正的差异化来自可信数据、好文案、审核和效果反馈闭环，而不是动画渲染本身。

## 局限与风险

- 完整的单字叙事模板只覆盖“懒”和“忙”；效果实验室额外使用六个汉字的路径，但没有证明长尾字符、包围结构、复合部件或自动布局已经通用化。
- “忙”字演示仍在 TSX 中硬编码笔画分组和位置，它是迁移实验，不是假装完成配置化的产品。
- 工作台只在浏览器中编辑与导出配置；当前没有服务端渲染 API，下载 JSON 不等于已经下载一条新 MP4。
- 姓名、日期和未来可能上传的照片都属于个人数据；正式产品必须定义保存期限、删除机制和隐私边界。
- 当前婚礼案例按临近日期假设年份为 2026，并使用“董小姐”展示称谓；正式公开或交付前必须由当事人确认完整信息、公开范围和照片授权。
- 效果实验室的跟写和多画幅章节明确属于视觉概念验证；目前没有真实笔迹识别、Alpha 编码或批量任务系统。
- TTS 依赖在线服务；音色、可用性和分词结果可能变化，脚本会在预期词序不一致时失败。
- “趣味拆字”容易被误解为字源，需要明确标签、来源字段和人工审核。
- 上游不提交 BGM；本研究的占位背景音只用于技术验证，不代表正式内容的听觉设计。
- `npm audit` 在固定依赖快照中报告 2 个 low、1 个 high 漏洞；本研究没有修改上游锁文件，生产使用前应升级并做渲染回归。
- 视频播放依赖浏览器媒体能力；展示页保留海报、文字结论和下载链接作为回退，但下载同样需要 MP4 资源可访问。
