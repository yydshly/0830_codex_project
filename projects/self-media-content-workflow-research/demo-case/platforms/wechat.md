## 正文

第一次看到 `genart-skill` 时，我也很容易把它理解成一种“能力插件”：装进 Claude Code，Agent 就会多一种生成艺术风格。

但当我把源码固定下来，真正运行检查器，再故意把确定性随机替换成 `Math.random`，这个判断发生了变化。

它没有带来一个新的图像模型。它带来的是一套让编码 Agent 更像专业生成艺术工作室的制度：知道该问什么、作品要暴露什么接口、最后怎样用浏览器验证。

### 先把“会生成”拆成三层

第一层是知识。

主 Skill 和参考资料告诉 Agent 如何处理 seed、命名随机子流、features、分辨率、平台约束与伦理问题。它们不会亲自画出一张图，但会改变 Agent 写代码时的默认决策。

第二层是协议。

一个 web sketch 只要接受 hash 和尺寸参数，提供重新渲染、读取 features、获取最终 Canvas 和完成信号，就可以接到统一的检查流程。这个协议很小，却是整个库最值得复用的部分：具体平台与工作室内部质检被解耦了。

第三层才是工具。

Playwright 会真的打开 Chromium，运行作品并读取 Canvas 原始像素。`check` 检查同一 hash 是否可复现、不同 hash 是否有差异、A-B-A 重渲染有没有全局状态污染，以及 features 是否稳定；`render` 则负责单图、网格、批量和 census。

这三层合在一起，才构成它真正增加的能力。

### 我为什么一定要做故障对照

只跑一遍绿色检查，很难说明检查器真的有效。于是我从正常 fixture 派生了一个故障版本，只做一件事：把 features 和 layout 使用的确定性随机流换成 `Math.random`。

结果不是“看起来有点不一样”，而是 4 项检查明确失败：重复性失败、A-B-A 全局状态检查失败、features 稳定性失败。与此同时，不同 hash 仍然能产生不同图像。

这个结果很重要。它说明 distinctness 通过，并不能证明作品确定；也说明多个互补测试不是形式上的清单。

### 500 个 seed 改变了观察尺度

只看一张图时，我们很容易围绕一个漂亮结果讲故事。9-seed 联系表开始暴露系列变化，而 500-seed census 把问题推进了一步：Palette 与 Density 到底以什么比例出现？

本次实测中，Ember 的目标权重是 45%，500 个 seed 中出现 44.4%；Aurora 的目标与实测都是 7.0%。这不构成统计学上的自动验收——上游工具并不会读取目标表做拟合检验——但它让“系列分布”第一次成为可以测量的对象。

配图：9 个确定性 seed 的联系表。网页交付资源为 `web/assets/genart-seed-grid.png`，原始研究证据为 `projects/genart-skill-research/artifacts/grid.png`。

### 边界比漂亮结论更重要

这次研究也遇到了上游 v0.1.0 在 Windows 上的 `ERR_HTTP_HEADERS_SENT`。为继续实验，我保留原始快照，只在实验副本里做了最小兼容修正。

更关键的是，当前像素检查证明的是固定 Chromium 环境中的同机复现。它不能自动推出不同浏览器、不同 GPU 的 WebGL 像素完全一致。Three.js、p5.js 和多个上链平台也主要由知识资料覆盖，不等于都有现成适配器和一键部署器。

### 我们真正应该学走什么

对我来说，这个库最有价值的并不是某个生成艺术提示词，而是它把专业能力拆成了可维护的结构：知识负责决策，协议负责接入，工具负责验证，人负责审美与授权。

这套结构也适合内容工作流、游戏资产和任何需要可复现输出的 Agent 系统。

下一次再看到一个 Skill，我不会先问“它是不是很强”，而会先问四件事：它增加了什么知识？规定了什么协议？提供了什么可执行工具？最后一步有没有真实权限？

答案清楚以后，宣传语就不再重要了。
