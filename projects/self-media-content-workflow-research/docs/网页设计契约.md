# 研究展示页设计契约

## Design Contract

- Entry mode：Brief-led implementation。
- Request revision：8。Revision 2 增加完整案例工作台；Revision 3 完成整体精修；Revision 4 补齐单一业务场景；Revision 5 增加生产前人工审核；Revision 6 收紧审核状态机；Revision 7 完成精准返工与案例总报告；Revision 8 根据“总结、沉淀、完善 Web、部署 GitHub”，补齐案例定位、两级来源索引、对外 README 引导、公开链接和 GitHub Pages 发布证据。
- Target user and context：需要快速理解该库的研究者、内容创作者、团队协作者和项目决策者；主要在桌面阅读，也会从手机打开分享链接。
- Desired first impression：这是一套可控、可追溯的端到端内容工作流，而不是“自动爆款和全平台群发”工具。
- Visual ambition：Editorial。
- Experience architecture：Editorial Flow。
- Visual constraints：研究期刊式层级；深蓝、纸白与信号橙；以 CSS、HTML 和内联 SVG 形成原创图解；不依赖外部图片服务；图形必须同时传递信息而非仅作装饰。
- Information constraints：先结论，再能力地图、运行原理、端到端样例、对我们的意义和能力边界；必须区分仓库能力、Agent 能力、条件能力和人工动作。
- Operation constraints：静态网页，无后端、登录或真实平台写入；核心交互用原生按钮、单选框和复选框实现并支持键盘；提供浅色/深色主题、能力模块选择、多平台样例切换和本地审核演练。
- State constraints：默认展示总控模块、小红书样例和 `AWAITING_USER` 审核状态；选中、悬停、键盘焦点和主题切换必须清晰；人工审核覆盖阶段未检查、确认未满足、可批准、退回修改、修订进行中、修订重新待审、已生成本地回执和整套重启；运行日志按当前会话记录关键事件，页面刷新不需要持久化演示决策。
- Environment constraints：零第三方依赖；由 `python -m http.server` 运行；页面位于 `projects/self-media-content-workflow-research/web/`，可被 Research Hub 复制到 GitHub Pages。
- Primary journey：概览用户在 3 分钟内完成“看懂总体定位 → 确认核心能力与自动化边界 → 看懂 9 个模块和原理 → 进入完整案例 → 核对来源与对我们的价值”；演示用户先明确 `genart-skill` 是可替换的真实案例原料，不是工作流依赖，再检查全部 9 阶段并进行批准或精准返工；最后在案例结论与来源索引中核对输入、产物、权限、上游仓库、固定提交和可复现文件。
- User-defined phases：网页整理、图解说明、样例展示、完整演示样例、继续优化和完善、用一个场景进行完整演示、继续补全、确定并补全、继续补充、确定补全案例、总结沉淀与 GitHub 发布。
- Required artifacts：`web/index.html`、`web/styles.css`、`web/app.js`、`web/demo.html`、`web/demo.css`、`web/demo.js`、`demo-case/scenario.md`、`demo-case/approval-record.md`、`demo-case/case-report.md`、`demo-case/` 完整文件包、`project.json` 上游索引、项目 README 对外引导、根 README 项目入口、静态验证脚本、浏览器验收记录、Research Hub 展示入口与 GitHub Pages 部署证据。
- Autonomy authorization：用户明确要求“完善我们的内容到 Web 中，部署到 GitHub 中并进行提交”，授权在现有研究子项目和根 README 中直接修订、验证、提交并推送本次交付。
- User-decision boundary：本次允许 GitHub 提交与 Pages 部署；仍不接入内容平台真实账号、发布接口、数据服务或付费媒体生成，不执行真实自媒体发布。
- Observable completion criteria：
  - 首屏无需滚动即可看见核心判断和端到端图；
  - 9 个 Skill 均可选择并展示输入、职责、产物和依赖；
  - 原理图展示总控、状态机、工具适配、人工确认和文件记忆；
  - 至少展示同一母题在小红书、公众号、短视频三种不同产物；
  - 完整案例工作台覆盖 9 个阶段，并能逐项查看真实输入、关键决策、完整产物与推进状态；
  - 小红书、公众号和短视频均提供可用成稿，短视频包含口播、镜头与字幕要点；
  - 发布阶段明确停在 `AWAITING_USER`，复盘阶段明确使用合成演示数据，不声称真实发布或真实表现；
  - 桌面 1440px、平板 768px、手机 390px 无遮挡和横向溢出；
  - 主题切换、能力选择和样例切换可通过鼠标和键盘完成；
  - `prefers-reduced-motion` 下不依赖动画传递信息；
  - 本地静态检查、Research Hub 检查和真实浏览器验收通过。
  - Revision 3 首屏标题在 1440 / 768 / 390 不出现孤字，首屏能直接读出 9 阶段、3 平台、8 个文件和 0 次外部写入；
  - 证据阶段用图解展示 A-B-A 确定性检查与 500-seed 分布，而不只是一组文字卡；
  - 平台阶段提供“目标 / 结构 / 证据 / 行动”的横向比较，能在一次扫描中说明三平台差异；
  - `#workbench`、`#artifact-index` 和各阶段深链接不会被粘性顶栏遮挡；
  - 状态变化通过标题、进度、可见面板、实时提示和 URL 一致反馈，不只依赖颜色。
  - Revision 4 只使用一个贯穿场景：Research Lab 已完成 `genart-skill` 研究，要在 90 分钟演示计划内形成三平台待发布包；
  - 场景页明确展示触发事件、参与角色、输入库存、限制条件、时间线、责任边界和完成定义；
  - 90 分钟必须标注为演示计划预算，不冒充真实耗时或效率承诺；
  - 交付文件从 8 项补全为 9 项，并包含独立 `scenario.md`；网页下载副本与源文件一致。
  - Revision 5 用可视映射说明四类研究输入分别进入哪些内容产物，并能从映射直接定位相应工作阶段；
  - 用户可以从场景入口启动演示、顺序浏览 9 阶段，并在浏览器内看到当前阶段和已检查数量的同步反馈；
  - 人工审核台必须要求选择一个主平台并确认事实、版权、平台适配和外部写入边界，条件不满足时不能生成批准回执；
  - 审核台支持“批准进入草稿”和“退回修改”两种本地演示决策，结果明确不等同于真实发布授权；
  - 交付文件增至 10 项，新增 `approval-record.md`，网页副本与源文件一致；
  - Revision 5 的桌面、平板、手机、双主题、键盘、状态切换、reduced-motion 与构建路由均通过真实浏览器验收。
  - Revision 6 在阶段检查不足 9 / 9 时，即使已选平台且完成 4 / 4 人工确认，批准按钮也必须保持禁用并说明缺少的阶段数；
  - 运行日志必须显示演示就绪、阶段首次检查、批准或退回、审核重置和整套重启事件，并始终显示外部写入为 0；
  - “重新开始完整演示”必须清除已访问阶段、平台选择、四项确认、退回原因、决策回执与旧日志，然后回到第 1 阶段和 1 / 9 状态；
  - 新门槛、日志和重启状态在桌面、平板、手机、双主题、键盘与 reduced-motion 下均可读、可操作，构建路由与源码页行为一致。
  - Revision 7 的四个退回原因分别路由到证据、素材、平台和质检阶段，并在回执中显示可操作的修订入口；
  - 开始修订时，目标阶段及其下游阶段必须从已检查集合移除，审核确认与退回原因清空，状态变为 `REVISION_IN_PROGRESS`；
  - 重新检查到 9 / 9 时，状态自动回到 `AWAITING_USER`，日志记录 `REVISION_READY_FOR_REVIEW`，必须重新完成 4 / 4 人工确认才能再次批准；
  - 网页案例结论集中说明真实输入、三平台产物、六道质量门、批准 / 返工分支、0 外部写入和“证明了 / 没证明”边界；
  - 交付文件增至 11 项，新增 `case-report.md`，源文件、网页副本和构建态保持一致。
  - Revision 8 在概览和案例页明确区分“研究对象 `self-media-content-workflow`”与“演示原料 `genart-skill`”，读者不需要上下文即可理解两者关系；
  - 页面提供上游仓库、固定提交、演示原料仓库、研究记录、完整案例和总报告的可点击来源索引，公开构建路由不依赖本地相对文档路径；
  - `project.json` 写入真实 `upstream_url`，根 README 项目索引显示“查看原库”，项目 README 首屏给出一句话结论、能力边界、样例定位与浏览入口；
  - 源码页和 Research Hub 构建态完成桌面、平板、手机、双主题、键盘、深链接与 reduced-motion 验收；GitHub 提交、推送和 Pages 工作流完成后核验公开 URL。

## 设计方向

| 决策 | 选择 | 原因 | 可观察约束 | 验收标准 |
| --- | --- | --- | --- | --- |
| 信息层级 | “结论 → 地图 → 原理 → 样例 → 意义 → 边界” | 先纠正对全自动发布的误解，再解释细节 | 首屏只有一个主结论 | 首次扫描能说出“完整架构，但执行依赖工具与授权” |
| 主视觉 | 端到端内容轨道图 | 直接表达从想法到复盘的关系 | 8 个阶段可读，不靠动画理解 | 桌面和手机均能读出顺序 |
| 能力地图 | 9 个模块组成的交互式系统图 | 比九段文字更容易理解路由关系 | 选择后有一致的详情反馈 | 9 个模块均可访问，选中状态清楚 |
| 样例 | 一个研究母题，三平台切换 | 证明“共享事实，不共享正文” | 三个平台内容结构明显不同 | 切换后标题、结构和行动同步更新 |
| 主题 | 浅色默认、深色可切换 | 适应长文阅读和演示环境 | 语义颜色不因主题改变 | 两个主题文字、边界和焦点可辨 |
| 动效 | 只用于选中和状态过渡 | 帮助理解状态变化 | reduced-motion 可关闭 | 关闭动效后内容和操作不丢失 |
