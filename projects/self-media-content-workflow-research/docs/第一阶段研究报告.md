# 第一阶段研究报告：能力、原理、场景与意义

## 1. 研究对象与判断口径

研究对象是 [`yanhua1010/self-media-content-workflow`](https://github.com/yanhua1010/self-media-content-workflow) 在提交 `c4602993ee744e3ceae4a9bfb8760b92d9338aad` 的源码快照，仓库版本为 `0.1.0`。

本报告把能力分为四层，避免把说明文档中的目标直接当成已经执行成功的功能：

| 层级 | 含义 | 判断方式 |
| --- | --- | --- |
| 仓库能力 | 仓库自身包含的 Skill、规则、模板和脚本 | 直接检查源码 |
| Agent 能力 | 安装后由 Codex、Claude Code 等模型理解并执行的流程 | 检查 Skill 契约，后续需运行实验 |
| 条件能力 | 必须依赖搜索、图片、视频、连接器、API 或账号授权 | 检查预检和降级路径 |
| 人工动作 | 项目刻意要求用户完成的确认、敏感素材上传和最终发布 | 检查状态机和安全边界 |

核心判断：它是一套声明式 Agent 工作流和内容运营 SOP。它能把想法编排到可发布成品，并在工具和授权满足时创建草稿或生成媒体，但不自带完成所有外部动作所需的服务和账号。

## 2. 能力梳理

### 2.1 总体闭环

[总控 Skill](../upstream/skills/self-media-content-workflow/SKILL.md) 定义了下面的主流程：

```text
需求澄清
→ 方向确认
→ 研究与证据
→ 平台确认
→ 发布预检
→ 平台原生初稿
→ 标题确认
→ 素材生成
→ 质量审校
→ 终稿确认
→ 发布授权
→ 草稿或发布包
→ 数据复盘
```

因此，“从想法到最终发布”在业务架构层面成立；在执行层面，应表达为“从想法到可发布成品，并在存在适配器和明确授权时写入草稿”。项目明确不执行无人值守群发。

### 2.3 平台能力

| 平台 | 已定义的内容能力 | 发布能力 |
| --- | --- | --- |
| X | 短帖、长帖、线程、开头与行动规范 | 默认手动发布包；有连接器时可扩展 |
| 小红书 | 搜索型标题、正文、组图信息任务、标签和视觉路由 | 默认手动发布包 |
| 微信公众号 | 深度文章、摘要、封面、移动端排版与图片处理 | 可通过 `wenyan CLI` 写入草稿箱，不群发 |
| 视频号 | 口播、分镜、字幕、封面和发布字段 | 默认手动发布包 |
| 抖音 | 前 3 秒钩子、口播、画面、字幕和发布字段 | 默认手动发布包 |
| B 站等其他平台 | 可以作为公开只读研究源 | 只有用户明确选择后才进入创作范围 |

### 2.4 内容生产能力

它处理的不只是正文，还覆盖：

- 账号定位和内容目标；
- 一次只推进一个母题；
- 事实、个人判断、推断与建议的边界；
- 内部生成 6 到 8 个标题并向用户展示 3 个；
- 多平台共享事实但重写正文；
- 8 套视觉风格预设及选择流程；
- 文案到画面的逐项映射；
- 短视频钩子、口播、镜头、字幕、BGM 和发布字段；
- 数字人肖像、声音权利、第三方数据处理和手动上传边界；
- 商业合作、AI/数字人和内容合规披露。

### 2.5 经营与复盘能力

[分析模块](../upstream/skills/self-media-content-analytics/SKILL.md) 接受后台截图、CSV、表格、公开链接或连接器数据。它要求：

- 区分曝光、阅读或播放、互动、关注、转化和制作成本；
- 只比较同平台、同内容类型和相近观察窗口；
- 优先使用中位数和 P75，不让一次爆款扭曲平均值；
- 使用每千浏览新关注、深度互动率和制作时间等标准化指标；
- 不把相关性直接称为因果；
- 每个周期只改变一个主要实验变量；
- 商单与自然内容分开分析。

这是一套稳健的分析纪律，但仓库没有自带数据采集服务和统计计算引擎。数据仍需用户、连接器或外部系统提供。

### 2.6 交付与记忆能力

工作流用 [内容任务卡](../upstream/skills/self-media-content-workflow/assets/content-task-template.md) 和 [内容注册表](../upstream/skills/self-media-content-workflow/assets/content-registry-template.md) 实现轻量持久化：

- 任务卡保存目标、证据、状态、标题、产物、确认、版本和复盘；
- 内容注册表每个母题一行，只保存索引和状态；
- 完整初稿、定稿、发布版和复盘作为里程碑保存；
- 文件保存后必须回读，确认存在、非空且素材路径有效；
- 单次用户修改只记为观察，用户明确确认或同类修改重复至少 3 篇后才升级为稳定偏好。

这让 Agent 可以跨会话恢复任务，但它仍是文件式状态，不是并发数据库、权限系统或机器学习模型。

## 3. 原理说明

### 3.1 声明式 Skill

每个模块由一个包含 `name` 和 `description` frontmatter 的 `SKILL.md` 定义。Agent 根据描述判断何时使用，然后读取正文中的步骤、输入、输出、边界和参考资料。

仓库一共包含：

- 9 个 `SKILL.md`；
- 17 份 `references/` 规范；
- 12 个 `assets/` 模板；
- 9 份 `agents/openai.yaml` 元数据；
- 1 个 Python 校验脚本。

唯一的 Python 脚本 [`scripts/validate.py`](../upstream/scripts/validate.py) 只校验 Skill frontmatter、目录名、元数据、行数、相对链接和 TODO。它不生成文章，也不调用平台发布接口。这证明仓库主体是“知识、流程和契约”，不是传统应用运行时。

### 3.2 总控路由与单一职责模块

总控只加载当前请求需要的模块。例如：

- 单篇创作：简报 → 平台文案；
- 账号冷启动：内容策略；
- 竞品分析：热点雷达；
- 视频：短视频模块；
- 数据复盘：分析模块。

这种设计减少了把所有平台规则同时塞进上下文的成本，也允许按需安装或替换单个模块。

### 3.3 状态机与人工确认

任务从需求澄清逐步流转到已复盘。以下状态转换必须由用户完成：

1. 确认创作方向；
2. 确认平台组合；
3. 选择或修改标题；
4. 确认终稿；
5. 授权创建草稿或进行其他外部写操作。

终稿确认不等于发布授权。数字人模式还要求用户本人在供应商平台手动上传、创建和选定头像与声音。

这种机制的目标是降低方向偏差、误发、账号风控和敏感素材泄露，不是追求最低的人机交互次数。

### 3.4 证据包与质量门

创作前建立证据包，记录可核验事实、个人经历、来源、不能证明的内容和读者收益。发布前再检查：

1. 事实与证据；
2. 账号声音；
3. 平台原生程度；
4. 标题、正文与视觉一致性；
5. 合规与商业披露；
6. 发布包完整性。

失败项必须记录修改动作和复检结果。质量门把“写完了”与“可以交付”分成两个状态。

### 3.5 工具发现、适配与降级

Skill 不写死某一家搜索、图片或视频服务，而是先检查当前环境：

```text
能力可用 → 调用已有工具执行
能力不可用 → 交付手动可完成的替代物
出现验证码、限流或风控 → 停止并交给用户
```

例如：

- 没有图片工具：交付视觉方案和提示词；
- 没有视频工具：交付脚本、分镜、字幕和素材清单；
- 没有数据接口：标记缺失字段，不估算；
- 没有发布连接器：交付手动发布包；
- 有 `wenyan` 和微信凭据：在二次授权后创建公众号草稿。

这是典型的“核心流程 + 运行时适配器”架构。它降低供应商锁定，但也意味着安装 Skill 本身不会自动获得外部工具权限。

### 3.6 文件式反馈闭环

发布数据被写回任务卡和指标台账，分析模块输出下一步动作与唯一实验；重复的人工修改和高表现模式经过最少样本要求后，才进入账号风格档案。

它不是模型训练，而是基于文件、规则和人工确认的显式学习闭环。优势是可审计、可修改；不足是需要维护文件一致性，复杂团队后期可能需要数据库和权限系统。

## 4. 使用场景

### 4.1 高匹配场景

#### 专业个人品牌

技术专家、产品经理、设计师、研究者和创业者可以把真实项目、失败复盘、方法和观点转成小红书、公众号、X 与短视频内容。证据优先设计尤其适合不能随意编造体验和结果的专业内容。

#### 一人公司和小型内容团队

团队可以用任务卡统一受众、目标、证据、标题、版本和发布状态，减少策划、文案、设计和发布之间的信息丢失。

#### 一个母题的多平台经营

同一研究成果可以共享事实资产，同时为每个平台重写表达，避免把长文章机械裁短后到处发布。

#### 有审核要求的内容

品牌合作、企业账号、数字人视频和涉及数据结论的内容，需要方向、终稿、披露和发布授权留痕，适合使用该状态机。

#### 需要长期复盘的账号

已经有一定发布量，能获得后台数据，并愿意按同类基线设计实验的账号，可以使用分析和风格学习模块形成持续改进。

### 4.2 低匹配场景

- 只偶尔写一条简单文案，不需要持久化和复盘；
- 追求无人确认、批量铺号和全自动群发；
- 希望自动点赞、关注、评论、私信或使用主账号批量采集竞品；
- 没有真实素材，却要求生成虚构体验、收益或用户评价；
- 认为安装 Skill 就等于获得所有平台 API、账号权限和媒体生成服务；
- 以短期数量为唯一目标，不能接受标题、终稿和发布前确认。

### 4.3 典型端到端案例

以一个软件项目失败复盘为例：

```text
项目 README、提交记录、截图和真实数据
→ 简报确认：面向谁、希望读者记住什么
→ 补充官方资料和可核验证据
→ 小红书：过程、反差、组图信息任务
→ 公众号：完整方法、决策与复盘
→ 短视频：一个判断、前 3 秒钩子、演示和字幕
→ 用户确认标题与终稿
→ 生成素材清单和手动发布包
→ 发布后记录收藏、分享、关注和制作时间
→ 下一轮只测试开头或封面中的一个变量
```

## 5. 对我们的意义

### 5.1 把研究成果转成持续内容

Research Lab 已经积累了源码研究、实验记录、截图、演示和结论。这些都是高质量一手证据。该工作流可以把每个研究子项目转成：

- 小红书的“能力拆解 + 实验结果”图文；
- 公众号的完整研究文章；
- X 的核心判断线程；
- 视频号或抖音的演示型短视频方案。

这能让“完成一个研究项目”同时积累项目资产和传播资产，而不是研究结束后再从零寻找选题。

### 5.2 为我们的 Agent 架构提供参考实现

它展示了一套值得复用的 Skill 设计方法：

- 一个总控负责路由，专业模块保持单一职责；
- 用任务卡而不是聊天记忆保存状态；
- 把关键外部写操作放在明确授权之后；
- 能力预检失败时有降级产物，不把整条流程卡死；
- 质量门记录失败、修复和复检，而不是只给一句“已检查”；
- 平台知识放进引用资料，核心 Skill 保持较短。

这些原则不只适用于自媒体，也适用于我们的图像、视频、游戏和产品研究 Skill。

### 5.3 从“提示词资产”升级为“运营系统”

单条提示词只能优化一次输出；这个库把账号定位、事实证据、风格偏好、任务状态、版本和发布数据连接起来。真正值得沉淀的是：

```text
真实项目与证据
+ 可复用的生产流程
+ 明确的人工决策点
+ 平台适配器
+ 发布后的反馈数据
```

这为我们建设个人或团队内容操作系统提供了现成骨架。

### 5.4 降低错误和账号风险

证据边界可以减少模型补造数据；两层发布授权减少误发；账号采集和发布权限分离减少主账号风险；数字人敏感素材不进入任务卡和仓库，降低肖像与声音泄露风险。

### 5.5 现实成本

采用它也会增加流程成本：

- 每篇内容需要维护任务卡和里程碑文件；
- 五个确认点会让单篇生产变慢；
- 平台连接器、账号凭据和 IP 白名单仍需单独配置；
- Markdown 状态适合个人和小团队，大规模协作需要数据库、权限和并发控制；
- 效果依然取决于一手材料、模型质量和人的编辑判断。

因此，它对我们的最佳定位不是“安装后自动运营所有账号”，而是“内容生产操作系统的基础协议和可改造骨架”。

## 6. 初步采用建议

不建议一开始就追求全自动发布。更稳妥的验证顺序是：

1. 安装总控、简报、平台文案和交付模块，先完成一个真实母题的多平台发布包；
2. 接入现有研究项目的 README、截图、实验数据和演示链接作为证据源；
3. 连续完成至少 3 个母题，验证任务恢复、用户修改和风格偏好；
4. 有稳定发布节奏后再接入数据复盘和内容日历；
5. 最后验证公众号草稿、视觉生成和视频合成适配器。

第一批试点可选择已经具有完整实验材料的研究项目。成功标准不是“自动发出去”，而是：同一母题能生成明显不同的平台原生稿，事实可追溯，发布包完整，下一次对话能够继续，并能用发布数据提出一个可验证实验。

## 7. 尚待验证

- 9 个 Skill 在 Codex 中的实际触发、路由和跨会话恢复效果；
- 不同模型执行同一状态机时的一致性；
- 小红书、公众号与短视频规范在真实发布界面的适配程度；
- `wenyan` 在当前 Windows 环境、公众号权限和 IP 白名单下的草稿链路；
- 真实改稿差异能否稳定转化为有用而不过拟合的风格偏好；
- 真实数据样本下，分析模块能否避免错误归因并给出有效实验。

这些问题属于下一阶段运行实验，不能仅凭源码说明直接判定已经通过。
