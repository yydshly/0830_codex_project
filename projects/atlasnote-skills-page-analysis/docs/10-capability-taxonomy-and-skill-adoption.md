# 从 81 项能力到我的 Skill

这份说明回答两个问题：怎样全量理解 Atlasnote Skills 页面中的 81 项，以及怎样把有价值的能力模式改造成自己的 Skill。

## 一、不要寻找唯一分类

每个模块至少有四个互补视角：

| 视角 | 回答的问题 | 类别与数量 |
| --- | --- | --- |
| 业务领域 | 它主要在解决谁的工作 | 设计与视频 24、工程开发 13、工具与元能力 12、研究与知识 11、写作与营销 8、产品与项目 7、文档与幻灯片 6 |
| 能力形态 | 它靠什么机制生效 | Skill 集合 17、端到端工作流 16、模板与设计系统 14、路由与元技能 8、评测与治理 7、确定性执行器 7、行为规则 5、外部连接器 5、知识系统 2 |
| 工作链角色 | 它在一次完整交付中负责哪一段 | 成果交付 24、专业方法 17、质量验证 15、工具执行 11、记忆与改进 7、路由与选择 5、目标与边界 2 |
| 采用方式 | 我应怎样把它带进自己的工作流 | 组合使用 41、借鉴改造 28、直接采用 7、先做集成 5 |

前三套分类描述模块本身；第四套分类描述你的采用决策。数量合计分别都是 81。

## 二、四种采用方式

### 1. 直接采用

主要对应边界清楚的确定性执行器。它们通常能把输入转成可观察输出，但仍需核对运行环境、写入范围、依赖和结果验证。

适合：浏览器自动化、本地渲染、格式转换、文件生成等可重跑任务。

### 2. 组合使用

主要对应工作流、Skill 集合和路由器。它们负责工作链的一段或一组方法，通常还需要目标、执行、验证或交付角色补齐闭环。

适合：软件交付、深度研究、产品推进、内容生产等多阶段任务。

风险：叠加多个同类“大合集”会造成触发冲突、步骤重复和上下文膨胀。

### 3. 借鉴改造

主要对应行为规则、模板与设计系统、评测器和知识系统。其价值通常在结构、约束和质量门，而不是原样安装。

适合：品牌规范、写作风格、评审清单、知识治理、任务质量门。

做法：保留模式，换成自己的对象、边界、交付物和验证；不要复制无许可的第三方指令、代码或资产。

### 4. 先做集成

主要对应外部连接器。没有实例、凭证、API、CLI、MCP 或写入权限时，它们只是能力说明，并没有真实执行价值。

适合：Google Workspace、飞书、n8n、学术检索、社交平台搜索等外部系统任务。

做法：先验证版本和认证，从只读、预览或 dry-run 开始，再明确外部写入和恢复边界。

## 三、最有效的理解顺序

```text
真实任务
→ 最近一次失败或返工
→ 缺口诊断（方法 / 工具 / 约束 / 验证 / 路由 / 记忆）
→ 用领域、形态和链路定位候选
→ 判断采用方式和权限
→ 选择 1～6 个互补模式
→ 生成最小 Skill 草案
→ 用一个真实任务和一个失败样例验证
→ 保留、修改或删除
```

目录适合侦察，不适合作为安装队列。最重要的单位不是“收藏了几个 Skill”，而是“哪一个重复任务因此更稳定、更快或更可证明”。

## 四、九种能力形态怎样落到真实资产

“能力形态”不是页面标签，而是不同的生效机制。判断一个模块时，应同时问它依靠什么生效、最小落地物是什么、失败风险在哪里。

| 形态 | 核心机制 | 最小落地物 | 常见风险 |
| --- | --- | --- | --- |
| 行为规则 | 用边界、禁止项和判断顺序约束行为 | 一组可执行规则与反例 | 规则宽泛、无法验证 |
| Skill 集合 | 把同类方法按任务入口组织 | 路由清晰的能力包 | 入口重叠、上下文膨胀 |
| 路由与元技能 | 先判断任务，再选择后续能力 | 触发矩阵与转交规则 | 误路由或过度路由 |
| 端到端工作流 | 固化阶段、顺序、停点与交付 | 阶段化流程和状态检查 | 流程过重、职责重复 |
| 确定性执行器 | 用脚本、CLI 或程序产生可观察输出 | 可重跑命令与结果校验 | 环境依赖、写入失控 |
| 外部连接器 | 通过 API、MCP 或凭证访问外部系统 | 认证、权限和只读试跑 | 权限、版本、不可逆写入 |
| 模板与设计系统 | 用结构和资产限制交付形态 | 模板、组件或 schema | 只复刻外观、忽略语义 |
| 评测与治理 | 用测试、清单或人工门禁判断成功 | 验收标准和失败样例 | 指标失真、检查流于形式 |
| 知识系统 | 用文件、索引或图谱保存可复用上下文 | 可检索知识与更新规则 | 过期、污染、来源不明 |

网页中的“九种形态落地字典”可以逐项展开，并直接把某一形态带入 81 项探索器；它回答的不是“长什么样”，而是“怎样工作、适合什么、至少需要什么、容易在哪里失效”。

## 五、六类缺口怎样诊断

先描述最近一次失败，再选择主要缺口。一次只抓最主要的一类，可以避免把所有能力都塞进同一个 Skill。

| 缺口 | 典型症状 | 优先形态 | 最先补的证据 |
| --- | --- | --- | --- |
| 方法 | 不知道专业步骤或判断依据 | Skill 集合、工作流 | 一次完整方法演练 |
| 工具 | 知道怎么做，但无法实际操作对象 | 执行器、连接器 | 可重跑输出或只读结果 |
| 约束 | 输出方向漂移、边界经常失守 | 行为规则、模板系统 | 反例、禁止项、结构校验 |
| 验证 | 做完了但无法证明质量 | 评测与治理、行为规则 | 验收清单和失败样例 |
| 路由 | 不知道什么时候调用哪个能力 | 路由与元技能、Skill 集合 | 正向与近似反向触发测试 |
| 记忆 | 每次都从头开始、经验无法复用 | 知识系统、模板系统 | 可检索记录和更新规则 |

网页的缺口诊断器会给出优先形态、最小产物、验证证据和不应做的事；“带入 Skill Builder”会同步主要缺口，但不会替你自动选择一大批模块。

## 六、怎样判断一个组合是否健康

Builder 现在会实时检查四件事：是否覆盖主要缺口、所选模块承担了多少不同工作链角色、是否在同一角色重复堆叠、是否包含需要凭证或外部实例的连接器。

检查结果分为四种可操作状态：

- **需要补缺：**当前组合没有覆盖主要缺口，只推荐一个最小优先形态；
- **职责集中：**多个模块挤在同一角色，先删重再扩展；
- **先核对依赖：**组合含连接器，先确认认证、版本、只读试跑和恢复边界；
- **组合聚焦：**主要缺口已覆盖，职责没有明显重复，可进入草案和真实任务验证。

这里不强求覆盖七段工作链。一个好 Skill 可以只负责其中一段，只要触发、交付和验证边界完整。

## 七、Skill 成熟度怎样推进

| 等级 | 状态 | 进入下一层的证据 |
| --- | --- | --- |
| L0 灵感 | 只知道一个有价值的模式 | 能说清真实重复任务 |
| L1 草案 | 有触发、步骤和交付物 | 正向与反向触发测试 |
| L2 可运行 | 能在项目内完成真实任务 | 可观察产物与验证记录 |
| L3 可依赖 | 多次稳定复用，失败可诊断 | 成功率、返工和人工干预数据 |
| L4 可演进 | 能由失败样本持续更新 | 版本、变更原因与回归样例 |

网页把这个阶梯放在诊断器旁边，提醒你：下载 `SKILL.md` 只是 L1，不等于已经获得稳定能力。

## 八、使用场景怎样把这些关系串起来

网页提供软件交付、深度研究、视觉内容、产品推进和知识学习五类场景。每类都不是“推荐几个热门模块”，而是沿同一条关系解释：真实输入是什么、最近为何失败、主要缺口是哪一种、什么能力形态能补缺、组合中的每项承担什么角色、最后拿什么证明完成。

个人场景映射器将五类工作对象与六类主要缺口交叉成 30 种关系。工作对象只决定案例上下文，主要缺口才决定优先能力形态；映射器据此推荐 3～5 项最小组合，并明确最小产物、完成证据和避免事项。

每个固定场景包含五步可播放演示；映射结果和固定演示都可把缺口、最多六项能力模式、任务、触发、交付和验证预填到 Builder。这样可以先从完整样例理解，再把它改成自己的任务。详细逐步示例见[使用场景对应关系与演示示例](11-scenario-relationship-demos.md)。

## 九、采用前怎样核验原始项目

Atlasnote 适合发现候选，但目录摘要不是安装证明。对一个准备采用的条目，至少核对以下字段：

1. 详情页究竟指向哪个官方仓库，项目身份是否一致；
2. 它真实属于规则、Skill、CLI、MCP、组件库、工作流还是复合系统；
3. 官方文档明确支持哪些事实，哪些只是目录转述或我们的推断；
4. 安装命令、运行时、依赖服务、凭证和外部写入权限；
5. 许可证、最近维护信号与已知风险；
6. 是否真的在当前环境运行过，以及用什么证据证明结果。

网页中的九类代表核验台把状态严格分为“官方来源已证实”“尚未验证”和“未在本项目运行”。它的目的不是给九个项目背书，而是示范怎样从目录侦察进入采用决策。完整档案见[九类代表项目原仓库核验](12-representative-source-verification.md)。

其余 72 项仍应视为待核验候选。若要落地为自己的 Skill，先借鉴可复用机制；只有确实需要其执行能力时，才进入安装、权限和真实任务试跑。

## 十、网页 Skill Builder 怎样用

1. 在 81 项清单中搜索真实任务涉及的对象或失败现象。
2. 用“采用方式”先排除当前无法落地的模块。
3. 点击“加入蓝图”，最多选择六项。优先让它们覆盖不同工作链角色。
4. 填写 Skill 名称、重复任务、触发边界、最终交付物和验证标准。
5. 选择主要能力缺口，生成 `SKILL.md` 草案。
6. 检查草案中的权限、停止条件、来源和支持资源建议。
7. 复制或下载草案，再用项目内 `$capability-to-skill` 元技能继续实现和验证。

生成器输出的是原创项目草案，不会自动安装 Skill、调用第三方工具或授予外部权限。

## 十一、项目内元技能的作用

[capability-to-skill](../skills/capability-to-skill/SKILL.md) 将“从外部能力得到启发”固化为一条可复用流程：

- 从重复任务而不是目录名称出发；
- 诊断主要缺口；
- 区分直接采用、组合、改造和集成；
- 选择最小 `SKILL.md`、`references/`、`scripts/`、`assets/` 或连接器组合；
- 对多模式组合做主要缺口、职责重叠、真实依赖和成熟度审计；
- 写清触发、交付、验证、权限与停止条件；
- 通过结构校验，并测试正向触发和近似但不应触发的任务。

它默认生成项目内草案，不会在未明确目标目录时静默写入全局 Skills 目录。

## 十二、进一步可扩展方向

1. **机器可读清单：**为每项增加许可证、版本、依赖、权限、输入、输出和验证字段。
2. **多标签能力图谱：**把前置、互补、替代、冲突和数据流做成关系图，而不只是一项一个主分类。
3. **任务到能力推荐：**从失败证据和目标反推最小能力链，并解释为何没有推荐其他候选。
4. **Skill 脚手架：**从网页蓝图生成完整目录，并调用结构校验器；涉及全局安装时单独确认。
5. **真实任务评测：**记录成功率、时间、返工、Token、人工干预和误触发。
6. **权限与供应链治理：**为脚本、MCP、凭证、外部写入、依赖版本和许可证建立门禁。
7. **会话反馈闭环：**从真实失败样本更新触发、步骤和验证，而不是凭感觉扩写说明。

## 十三、对你的直接意义

你已经习惯把网页和开源项目拆成研究子项目。这个工作台把下一步补上了：研究结论不再停在“我看懂了”，而是能沿着同一条路径变成项目内、可检查、可继续迭代的能力资产。

当前最值得沉淀的三项个人资产是：

1. **网页能力分析：**从页面证据提取能力、机制、场景、边界和证据等级；
2. **研究转交付网页：**把研究结论重组为可探索、可诊断、可操作的网页，而不是堆砌文档；
3. **能力模式转 Skill：**从真实失败出发，选择最小模式，完成触发、依赖、验证和成熟度审计。

最值得优先沉淀的不是通用大合集，而是你每周重复、返工明显、完成标准可以说清楚的一项任务。
