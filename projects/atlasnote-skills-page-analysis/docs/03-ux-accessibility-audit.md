# UX、视觉与可访问性审计

## 1. 审计范围

- 产品表面：Atlasnote Skills 目录与单个详情页。
- 用户目标：找到一个可能适用的 Agent Skill / 工作流项目，理解其价值并进入原仓库。
- 视口：1440×1000 桌面端、390×844 移动端。
- 状态：未登录公开页面。
- 模式：UX 与可访问性联合审计。

## 2. 逐步体验与健康度

| 步骤 | 状态 | 观察 | 健康度 |
| ---: | --- | --- | --- |
| 1 | 进入目录首屏 | 定位、分类、搜索和首批卡片在一个视口内可见 | 良好 |
| 2 | 选择“设计与视频” | 结果数从 81 更新为 28，卡片立即重排 | 良好 |
| 3 | 搜索 `PPT` | 返回三种不同交付路线，搜索框有清晰焦点环和清除按钮 | 良好 |
| 4 | 输入无匹配关键词 | 空状态解释清楚，但结果上下文文案拼接不自然 | 一般 |
| 5 | 展开更多筛选 | 只多出“其他 3”；“更多筛选 1”含义不够直观 | 一般 |
| 6 | 打开详情页 | 先展示“交付什么”，再给摘要、标签和 GitHub CTA | 良好 |
| 7 | 阅读详情正文 | 使用示例、作者、Star、版本和同类项目完整 | 良好 |
| 8 | 移动端浏览目录 | 分类换行、搜索和单列卡片保持清楚 | 良好 |
| 9 | 打开移动菜单 | 导航、登录和语言集中；关闭入口明显 | 良好，焦点行为未验证 |

## 3. 已确认的优点

### 3.1 首屏说明了“这里能解决什么”

页面没有先解释规范、文件结构或生态历史，而是用“做幻灯片、写代码、做设计、跑调研”建立用户预期。这对非开发者很友好。

### 3.2 信息架构支持从宽到窄

用户可以先按大类浏览，再用关键词缩小，最后进入详情。分类按钮同时显示数量，降低了点击的不确定性。

### 3.3 卡片高度和字段一致

不同来源的项目被压缩成统一结构，用户可以快速扫标题、摘要、作者和流行度。卡片整体可点击，目标区域足够大。

### 3.4 搜索反馈即时

结果数量、卡片和空状态都会跟随输入更新。`PPT` 的三个结果展示了搜索对中文标题、英文缩写和摘要内容的综合匹配价值。

### 3.5 详情页以结果而非技术开场

顶部“交付什么”把最重要的价值判断提前。GitHub CTA 在摘要之后出现，既避免过早跳走，也不会让已经理解的用户寻找太久。

### 3.6 移动端没有丢失核心功能

分类、搜索、卡片和详情页都保留；导航被折叠，卡片变为单列，重点顺序合理。

## 4. UX 风险

### P0：没有明确解释“这是第三方目录，不是直接安装和执行平台”

标题和副标题容易让用户产生“一键装上”的预期，但核心 CTA 只是“在 GitHub 查看”。建议在目录首屏或卡片附近增加一句：

> 本页收录第三方开源项目。Atlasnote 提供中文解读；安装、权限和使用请以原仓库为准。

### P0：项目形态混在一起

Skill、Skill 集、CLI、MCP、浏览器扩展、框架、模板库和完整应用被统一称为“技能”。这会直接影响用户判断成本。

建议在卡片与详情页增加类型徽标：

```text
Skill · Skill 集 · Plugin · MCP · CLI · 模板库 · 框架 · 应用
```

### P0：缺少安全试用所需的元数据

GitHub 跳转之前应至少展示：

- 兼容客户端；
- 许可证；
- 安装范围；
- 外部依赖；
- 是否运行脚本；
- 是否需要联网或 API Key；
- 最近人工验证时间；
- 风险提示。

### P1：默认排序缺少解释和控制

当前列表视觉上接近按 Star 排序，但没有明确排序控件和策展逻辑。用户很容易把 Star 当质量分数。

建议提供：精选、最近验证、最近更新、Star、安装成本、无需外部依赖等排序或快捷筛选。

### P1：空结果上下文文案不自然

搜索无结果时，数量行疑似把查询词直接拼接在“共 0 个”之后。空状态正文是清楚的，但上方文案会降低完成感。

### P1：“更多筛选 1”语义模糊

数字 1 表示一个隐藏分类，而不是一个已应用条件。可以改成“更多分类”或直接显示“其他”，避免额外一次点击。

### P1：详情页仍停留在“读懂”，没有帮助“做决定”

除了 GitHub，没有安装说明、兼容性、试用难度、前置条件或验证状态。可以增加一个“使用前检查”区块，将用户带到更有把握的下一步。

### P2：分类重叠没有解释

多标签本身是合理的，但数量总和明显大于 81。建议在分类下增加简短提示：“一个项目可属于多个分类”。

### P2：同类技能推荐缺少推荐理由

详情页底部列出四个“同类技能”，但相似关系并不总是显然。增加“同类原因”或按“替代方案 / 配套工具 / 更轻量”分组，会提高推荐可信度。

### P2：登录价值不明确

登录按钮全站突出，但目录内没有展示登录后可以收藏、订阅更新、比较或生成推荐。如果账户能力确实存在，应在用户需要时解释收益；如果不存在，登录不应抢占主要注意力。

## 5. 可访问性观察

### 5.1 从本次证据可确认的优点

- 页面存在明确的一级和二级标题结构。
- 分类和更多筛选使用按钮语义。
- 更多筛选和移动菜单暴露了展开状态。
- 搜索框暴露为 searchbox，并具有可见焦点环。
- 卡片整体为链接，点击目标较大。
- 移动端提供明确的菜单与关闭按钮。
- 桌面与移动端都保持阅读顺序基本一致。

### 5.2 需要进一步验证的风险

- **选中状态**：可访问性快照中，分类按钮没有看到 `pressed` 或等效状态；当前选中主要靠深色背景表达。
- **对比度**：分类数量、灰色说明文字和部分标签颜色较浅，需要实际测量 WCAG 对比度。
- **移动菜单焦点**：截图不能证明焦点被限制在菜单内，也不能证明背景内容设置了 `inert` 或正确隐藏。
- **卡片链接名称过长**：整张卡片的可访问名称包含标题、摘要、作者和 Star，屏幕阅读器用户可能需要听很长内容才能到下一张。
- **触控目标**：部分分类文字看起来接近最小目标高度，需要测量是否满足 44×44 CSS 像素建议。
- **图片替代文本**：视觉截图无法确认所有预览图是否具有恰当 alt；如果整卡已是描述充分的链接，装饰性图片应避免重复朗读。
- **缩放与重排**：只检查了两个视口，未验证 200%/400% 缩放和横屏。
- **动态结果通知**：搜索结果即时变化，但未验证屏幕阅读器是否会收到结果数量更新。

本审计不能据此声明 WCAG 合规。还需要键盘全流程、屏幕阅读器、对比度、缩放和动态状态通知测试。

## 6. 结构问题与视觉润色问题

### 结构问题

- 第三方目录边界不清；
- 项目类型混合；
- 缺少安装和风险元数据；
- 排序逻辑不透明；
- 详情页缺少决策支持。

### 视觉与文案问题

- 空结果数量文案；
- “更多筛选 1”的命名；
- 分类数量对比度；
- 同类推荐理由；
- 登录价值说明。

结构问题会影响信任和选择，应先于卡片阴影、间距或动效等视觉微调。

## 7. 优先级建议

| 优先级 | 改进 | 用户收益 | 实施复杂度 |
| --- | --- | --- | --- |
| P0 | 明确第三方目录边界 | 避免误解产品能力 | 低 |
| P0 | 增加项目类型徽标 | 快速判断安装与使用形态 | 中 |
| P0 | 增加兼容性、依赖、许可证、验证日期 | 支持安全决策 | 中至高 |
| P1 | 提供排序和高级筛选 | 降低 81 项浏览成本 | 中 |
| P1 | 修复零结果文案 | 提高搜索完成感 | 低 |
| P1 | 增加“使用前检查”和安装指引 | 提高详情到试用的转化 | 中 |
| P2 | 解释多标签和相关推荐关系 | 提高信息可信度 | 低 |
| P2 | 增加收藏、比较和更新订阅 | 支持回访和长期决策 | 中至高 |

## 8. 证据限制

- 没有登录，未检查账户功能。
- 没有执行任何第三方安装或 GitHub 写操作。
- 只深查了一个详情页，不能保证所有详情页字段完全一致。
- 未检查源代码、后端数据模型、缓存、SEO 实现或真实分析事件。
- 未运行屏幕阅读器和自动对比度测试。
- 未测试慢网、离线、图片加载失败和异常网络状态。
