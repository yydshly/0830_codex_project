# 能力到底是什么

## 1. 先纠正一个容易产生的误解

Atlasnote 的卡片不是 81 张功能截图，也不是 81 个完全同类的软件插件。它们是 81 个“让 Agent 更可靠地完成某类任务”的方案样本。

这里的“能力”应定义为：

> 在明确触发条件下，使 Agent 能以更稳定、可执行、可检查的方式改变输入、外部系统或交付物的一组方法与资源。

它不一定让模型知道更多，也不一定需要训练模型。多数能力来自下面六种增量：

1. **上下文增量**：告诉 Agent 当前产品、用户、品牌、代码库或研究对象是什么。
2. **程序增量**：把专家经验写成顺序、分支、循环、停点和失败处理。
3. **工具增量**：通过脚本、CLI、浏览器、MCP 或 API 让 Agent 能读写外部世界。
4. **约束增量**：限制布局、配色、文件范围、修改幅度、依赖或权限。
5. **验证增量**：用测试、规则、评分、评审或人工确认判断是否合格。
6. **资产增量**：提供模板、组件、参考文件、设计系统和可复用素材。

因此，“装了一个 Skill”不等于安装了一个新模型。更准确的比喻是：给同一个人配了一份 SOP、一套工具、几张表格和一个质检员。

## 2. 一个能力包由什么组成

成熟的能力包通常包含以下部件；并非每项都有。

| 部件 | 回答的问题 | 常见实现 | 缺失后的结果 |
| --- | --- | --- | --- |
| 身份与触发 | 什么时候该用我？ | 名称、描述、触发条件、适用/不适用 | Agent 不会加载或乱触发 |
| 输入契约 | 开始前必须知道什么？ | 必填字段、澄清问题、上下文文件 | 猜需求、默认值失真 |
| 方法与步骤 | 应按什么顺序做？ | `SKILL.md`、检查清单、状态机 | 每次做法不同、漏步骤 |
| 执行工具 | 怎样改变真实世界？ | scripts、CLI、MCP、API、浏览器 | 只能给建议，不能完成动作 |
| 资源与资产 | 参考什么、复用什么？ | references、模板、组件、样例 | 输出漂移、重复造轮子 |
| 输出契约 | 最后交付什么？ | 文件格式、目录、字段、渲染要求 | “做完了”但不可用 |
| 质量门 | 怎样知道成功？ | 测试、lint、规则、评分、人工批准 | 错误直接流入最终产物 |
| 失败与恢复 | 出错怎么办？ | dry-run、重试、回滚、暂停条件 | 自动化越强，事故越大 |
| 反馈与改进 | 下一次怎样更好？ | 会话抽样、指标、复盘、版本更新 | Skill 长期僵化 |

## 3. 生效原理：渐进加载，而不是把全部内容塞进提示词

开放的 Agent Skills 结构通常以一个目录为单位，核心是 `SKILL.md`，可选地携带 scripts、references 和 assets。理想运行方式是渐进披露：

```text
发现阶段：只看到名称与简述
        ↓ 命中任务
激活阶段：加载完整 SKILL.md
        ↓ 需要执行或查证
执行阶段：再读取参考资料、运行脚本、调用外部工具
```

这样做有三个好处：

- 避免 81 项同时占用上下文；
- 只有任务相关能力进入当前回合；
- 大型参考资料和脚本按需读取，方法与执行可以分开维护。

真正的运行时可以抽象为：

```text
用户任务
  → 路由：此刻需要哪项能力？
  → 契约：输入够不够，边界是什么？
  → 方法：按什么步骤与分支推进？
  → 工具：读写哪些文件、网页、系统或 API？
  → 验证：测试、规则和人工门是否通过？
  → 交付：产生什么可用文件或状态？
  → 复盘：保存证据并改进下一版能力。
```

## 4. 两张地图必须同时看

### 地图 A：业务领域

Atlasnote 页面使用工程开发、设计与视频、产品与项目、内容与知识、写作与研究、营销增长、文档与幻灯片等分类。这回答“它服务什么工作”。

### 地图 B：能力形态

更重要的是它通过什么方式产生效果：

| 能力形态 | 本质 | 代表条目 |
| --- | --- | --- |
| 行为规则 | 给 Agent 一组可检查的纪律 | Karpathy 四原则、Stop Slop |
| 单项 Skill | 完成边界清楚的重复任务 | SwiftUI 审查、`/goal` 指令 |
| Skill 集合 | 按领域提供多个独立方法 | Matt Pocock、Vercel、Waza |
| 路由与元技能 | 判断每回合加载哪一项 | 29+1 路由、n8n 元技能 |
| 端到端工作流 | 串起多个阶段、角色和检查点 | gstack、学术流水线、视频剪辑 |
| 确定性执行器 | 用 CLI、脚本或引擎稳定执行 | Agent Browser、HyperFrames、AI 检测引擎 |
| 外部连接器 | 经 MCP/API 操作真实服务 | n8n、Stitch、论文检索 MCP |
| 模板与设计系统 | 用固定资产和选择空间约束输出 | PPT 模板、不二设计系统、Kami |
| 评测与治理 | 检查产物或改进 Skill 本身 | Impeccable、Skill Doctor、Keel |

同一条目可能同时占两到三种形态。比如 Impeccable 同时有 Skill、CLI、浏览器扩展和确定性规则；SwarmVault 同时是 CLI、MCP、桌面应用和知识图谱。

## 5. 怎样判断它有没有“真实能力”

看完描述后，用下面五级判断，不要只看名称和 Star：

| 等级 | 能力证据 | 典型表现 |
| --- | --- | --- |
| L0 灵感 | 只有观点或提示词 | 可启发，但结果高度依赖模型临场发挥 |
| L1 程序 | 有步骤、输入和输出约定 | 能提高一致性，但未必能执行外部动作 |
| L2 执行 | 有脚本、CLI、MCP 或 API | 能产生真实状态变化或确定性文件 |
| L3 验证 | 有测试、规则、评分或人工门 | 能证明一部分结果，而非只声称完成 |
| L4 闭环 | 有监测、复盘、版本与恢复机制 | 能长期运行并根据失败证据改进 |

L4 不一定永远最好。一次轻量写作修订用 L1 足够；高风险发布、安全审计或批量写操作则至少需要 L3，并保留人工批准。

## 6. 这个目录真正提供的能力

Atlasnote 自身不负责运行多数项目。它提供的是“发现与理解能力”：

- 把 GitHub 项目翻译成结果语言；
- 暴露项目之间的能力模式；
- 帮助用户形成候选和搜索词；
- 让人看到任务还可以怎样被流程化。

它尚不能替代原仓库审查、兼容性确认、安全检查和真实任务评测。所以最合适的定位是能力侦察地图，而不是安全认证商店或统一运行时。

## 7. 读一个模块时只问这八个问题

1. 它改变的是 Agent 的判断、动作、记忆、交付还是验收？
2. 它是说明文件、工具、连接器、模板、工作流还是应用？
3. 触发条件和不适用条件是否明确？
4. 需要什么账号、运行时、密钥和外部实例？
5. 会读取和写入什么数据？
6. 产物是否真正可编辑、可执行或可复现？
7. 它如何证明成功，失败如何停止或恢复？
8. 能否拆出最小可用部分，改成自己的资产？
