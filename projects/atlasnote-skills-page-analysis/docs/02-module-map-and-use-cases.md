# 模块地图与使用场景

## 1. 为什么看起来像有很多“模块”

目录中的每一张卡片代表一个独立项目，但这些项目不是同一种东西。更准确的理解方式不是记住 81 个名字，而是先判断它属于哪种能力形态。

## 2. 九类能力形态

| 能力形态 | 它真正提供什么 | 页面中的代表例子 | 适合场景 | 主要风险 |
| --- | --- | --- | --- | --- |
| 单项 Skill | 一套任务说明和验收纪律 | 写作去 AI 腔、代码审查、目标指令 | 一个边界清楚的重复任务 | 触发描述不准、只写规则不验证 |
| Skill 集合 | 多个可以组合的专业流程 | Matt Pocock Skills、Vercel 前端技能 | 覆盖完整工作阶段 | 一次装太多、规则冲突 |
| 路由 / 元技能 | 根据上下文选择下一条 Skill | 单路由技能、PM 插件市场 | 用户不知道该走哪条流程 | 路由误判、上下文成本 |
| 端到端工作流 | 把多个阶段和检查点串起来 | gstack、/spec 到 /ship、学术流水线 | 需要从输入推进到最终交付 | 流程过重、失去人工控制 |
| 确定性 CLI | 通过命令稳定操作浏览器或外部服务 | Agent Browser、Workspace CLI、飞书 CLI | 需要可重复、可脚本化执行 | 环境安装、权限和 API 依赖 |
| MCP / 外部集成 | 把 Agent 接到真实系统 | n8n、Stitch、论文检索 MCP | 操作 SaaS、数据库或工作流实例 | 凭据、网络、写操作和版本要求 |
| 模板 / 资产系统 | 约束输出样式并复用素材 | PPT、海报、插画、设计系统 | 品牌一致、稳定生成视觉产物 | 风格僵化、版权和素材依赖 |
| 审计 / 质量门 | 在交付前检查问题 | Impeccable、代码审查、安全插件 | 高质量要求、上线前检查 | 规则覆盖有限、误把检查当证明 |
| 应用 / 框架 + Skill 指南 | 既有运行时，再附 Agent 使用方法 | Remotion、shadcn/ui、SwarmVault | 需要真实软件能力而非只靠提示词 | 容易误以为 Skill 本身就是产品 |

这一分类解释了为什么“shadcn/ui”和“写作检查清单”会出现在同一目录：页面按“能帮助 Agent 完成什么”聚合，而不是按软件包形态分类。

## 3. 七个主分类分别有什么参考意义

### 3.1 工程开发

解决 AI 编码常见的四类问题：

- 需求理解错；
- 实现跨度过大；
- 缺少测试和反馈循环；
- 代码能跑但结构持续恶化。

适合：真实代码仓库、重构、debug、代码审查、架构治理、发布流程。

参考价值：学习如何把“写代码”拆成规格、实施、测试、审查和回滚，而不是只给模型一句需求。

### 3.2 设计与视频

解决 AI 视觉输出的模板感、不一致和不可编辑问题。

适合：落地页、设计系统、UI 审查、动效、插画、Logo、React 视频和短视频工作流。

参考价值：理解视觉任务为什么需要方向选择、约束旋钮、人工确认、预览和最终渲染，而不是一条超长提示词。

### 3.3 产品与项目

解决模糊想法难以进入执行的问题。

适合：PRD、需求访谈、任务拆分、优先级、阻塞关系、项目跟踪和决策记录。

参考价值：学习如何把讨论转成可检查的规格和工作项，并保留人类决策点。

### 3.4 内容与知识

解决资料分散、知识不可检索和跨会话丢失的问题。

适合：代码知识图谱、Obsidian、知识库、长期记忆、内容归档和报告生成。

参考价值：区分“把资料塞进上下文”和“建立可追溯、可更新的知识结构”。

### 3.5 写作与研究

解决调研缺少证据、写作风格漂移和学术诚信问题。

适合：深度调研、论文检索、研究大纲、引用管理、内容修订和 AI 写作检测。

参考价值：借鉴来源等级、阶段性产物、审查门和最终定稿之间的关系。

### 3.6 营销增长

解决营销活动彼此割裂、不了解产品底座的问题。

适合：SEO、广告、转化率、内容分发、留存、销售运营和跨境电商。

参考价值：优秀的营销 Skill 不从写文案开始，而是先读取产品、受众、定位和渠道约束。

### 3.7 文档与幻灯片

解决“AI 只给文本，不能交付可编辑成品”的问题。

适合：原生 PPTX、网页演示、PDF、Word、信息图和文档设计系统。

参考价值：判断交付物到底是可编辑文件、单页 HTML、整页图片还是模板替换，避免对“生成 PPT”产生错误预期。

## 4. 从任务形状选择模块

| 你的问题 | 优先找什么 | 不要先找什么 |
| --- | --- | --- |
| AI 总误解需求 | 需求澄清、规格、访谈 Skill | 更强的代码生成 Prompt |
| 产出每次风格不同 | 设计系统、模板、品牌约束 | 随机灵感生成器 |
| 经常出现不可复现 bug | TDD、诊断循环、浏览器 QA | 一键重写整个模块 |
| 外部系统无法操作 | CLI、MCP、连接器 | 只包含 Markdown 的 Skill |
| 不知道该选哪条流程 | 路由 / 元技能 | 同时激活几十个 Skill |
| 需要长期知识积累 | 知识图谱、记忆、引用系统 | 把全部资料长期塞进 Prompt |
| 需要可交付文件 | 原生文档 / 渲染工具 | 只生成内容大纲的 Skill |
| 输出风险高 | 审计、质量门、人工审批 | 完全自动执行的流水线 |

## 5. 典型使用场景

### 场景 A：为 Codex 找一个工程工作流

目标：减少需求误解和返工。

流程：

1. 在“工程开发”搜索规格、TDD 或 bug。
2. 比较轻量 Skill 与端到端流水线。
3. 查看是否兼容 Codex、是否要求 issue tracker 或额外 CLI。
4. 只安装最小集合。
5. 用一个真实改动比较安装前后的返工次数和测试结果。

### 场景 B：改善 AI 网页的模板感

目标：让生成页面具备明确视觉方向。

流程：

1. 在“设计与视频”寻找设计系统、改版审计或视觉方向选择。
2. 区分“只出参考图”和“直接写代码”的项目。
3. 确认是否依赖图像生成、GSAP、组件库或浏览器工具。
4. 先生成候选方向，再选中一个实现。

### 场景 C：把资料做成 PPT

目标：从材料得到可编辑演示文稿。

`PPT` 搜索至少出现三种路线：

- 原生 PowerPoint；
- 网页幻灯片；
- 锁定视觉系统的单文件 HTML。

选择时应先回答：是否必须 `.pptx`、是否需要离线播放、是否要继续编辑、是否允许网页交付，而不是只看 Star。

### 场景 D：搭建研究流程

目标：让调研结果有来源、过程和审查。

优先选择具备以下结构的项目：

- 先生成大纲；
- 中间产物可保存；
- 搜索与写作分开；
- 引用原始来源；
- 有完整性或诚信检查；
- 能明确说明没有找到什么。

### 场景 E：建立团队内部 Skill 库

目标：让团队重复任务按统一标准执行。

可以借鉴此页面的字段结构，但应增加内部信息：负责人、适用项目、数据边界、权限、版本、评测结果、回滚方法和废弃状态。

## 6. 不适合使用目录的情况

- 只是一次性的简单问答；
- 任务尚未定义，连预期输出都不清楚；
- 希望网页直接替你运行第三方 Skill；
- 没有时间审查陌生脚本和依赖；
- 涉及高风险写操作，却没有权限控制和人工审批；
- 只因为 Star 高就准备全局安装。

## 7. 读卡片时应问的七个问题

1. 它是 Skill、CLI、MCP、模板、框架还是完整应用？
2. 它解决的是我的真实问题，还是只是看起来很先进？
3. 它最终交付什么文件或状态？
4. 它需要哪些工具、账号、密钥和运行时？
5. 它会读取或写入哪些数据？
6. 它怎样证明成功，失败时怎样停止或恢复？
7. 我能否把它改成自己的流程，而不是被它接管？
