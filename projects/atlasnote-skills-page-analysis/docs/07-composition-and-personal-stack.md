# 能力组合方式与个人能力栈

## 1. 不要按“装了多少”思考，要按“工作链缺哪一环”思考

单个模块通常只负责一小段。组合的目标不是让 Agent 看起来全能，而是让一项真实任务从模糊输入走到可验证交付。

```text
目标与边界
   ↓
上下文与专业方法
   ↓
计划、路由与人工决策
   ↓
CLI / 脚本 / MCP 执行
   ↓
测试、规则、评审与人工门
   ↓
可编辑交付物
   ↓
证据、记忆与 Skill 改进
```

每一层最多先选一个主模块。只有在真实任务证明缺口存在时，再增加第二个。

## 2. 六层能力角色

| 角色 | 它负责什么 | 页面中的样本 | 组合原则 |
| --- | --- | --- | --- |
| 目标器 | 把模糊意图写成结果、约束和完成条件 | `/goal`、PRD、规格 Skill | 所有长任务先明确成功与停止条件 |
| 路由器 | 选择当前该加载什么能力 | 29+1、n8n 元技能、Remotion best-practices | 每轮少加载，避免同类规则同时争夺控制 |
| 专家方法 | 提供领域步骤和判断框架 | Waza、Vercel、科研技能、营销技能 | 只选与任务直接相关的最小子集 |
| 执行器 | 改变文件、浏览器、API、实例或渲染物 | Agent Browser、飞书 CLI、MCP、HyperFrames | 执行权限与说明规则分离，默认最小权限 |
| 质量门 | 判断能否进入下一阶段或交付 | 测试、Impeccable、诚信门、Keel | 高风险阶段设置阻断式门，不只给建议 |
| 记忆与改进 | 保存来源、理解和失败证据 | SwarmVault、Understand Anything、Skill Doctor | 只记录可追溯信息，用真实失败更新 Skill |

## 3. 典型组合方案

### A. 软件功能从需求到发布

```text
/goal 或规格 Skill
→ Matt Pocock / Waza 选择一个小工程流程
→ shadcn/ui、Supabase、GSAP 等领域能力按需加入
→ Agent Browser 做真实浏览器 QA
→ Thermo-Nuclear / Keel 按风险做结构审查
→ Skill Doctor 从失败会话改进规则
```

适用：真实代码仓库的功能、重构和发布。

关键判断：gstack 已覆盖许多阶段，采用它时不要再把多个同类全流程套件叠上去；否则命令、状态和验收标准会互相冲突。

### B. 深度研究到可交付报告

```text
/goal 明确研究问题、来源边界和完成条件
→ 大纲先行的深度调研建立 JSON 中间产物
→ last30days 获取近期讨论；论文 MCP 获取学术来源
→ 学术诚信门检查来源、引述和未证实断言
→ PPT Master / Frontend Slides / HTML Anything 生成交付物
→ SwarmVault 保存来源与结论关系
```

适用：行业研究、竞品研究、技术调研、学术综述。

关键判断：搜索、综合、写作、排版应分开。让同一个回合边搜边写，最容易产生来源漂移和早下结论。

### C. 品牌视觉与内容生产

```text
品牌上下文和受众
→ 风格试衣间生成互斥方向，人工选择
→ UI UX Pro Max / Taste / 不二设计系统建立约束
→ Logo、IP、插画或 Remotion 能力生产资产
→ Impeccable、真实尺寸预览和人工品牌审查
→ 模板/角色基线进入长期资产库
```

适用：网站、系列海报、内容 IP、品牌视频。

关键判断：视觉任务最重要的能力常常不是“一次生成”，而是让用户在低成本阶段选择方向，以及保持后续系列一致性。

### D. 产品管理与项目推进

```text
访谈/需求澄清
→ PRD 或 PM 工作流形成中间产物
→ 任务、风险、依赖和验收标准
→ 飞书等 CLI 写入真实协作系统（先 dry-run）
→ 阶段评审与决策记录
→ 复盘后更新模板和路由规则
```

适用：从想法到研发交接、路线规划和跨团队推进。

关键判断：PM Skill 的价值不在生成更多文档，而在于把讨论转成可检查的决策、依赖和状态变化。

### E. 持续营销增长

```text
product-marketing 共享底座
→ SEO / 广告 / 内容技能按目标路由
→ 外部平台工具执行
→ 真实转化、成本和留存指标
→ 目标循环决定继续、调整或停止
```

适用：长期内容、SEO、广告和增长实验。

关键判断：先建立共享产品上下文和预算/停止条件；否则 49 条技能只会规模化地产生互相矛盾的内容。

### F. 个人知识与学习系统

```text
Obsidian 原生格式或 SwarmVault 摄入资料
→ 来源标签、链接和图谱
→ 针对当前任务检索，而非全量塞入上下文
→ 完成工作后触发短练习
→ 真实会话由 Skill Doctor 找出能力缺口
```

适用：长期研究、代码库理解、学习和个人知识管理。

关键判断：知识库真正困难的是更新、冲突、删除和来源，而不是第一次导入。

## 4. 对你的直接意义

结合你当前把网页拆成独立研究子项目、让 Codex持续积累材料的工作方式，这个页面至少有五层参考价值。

### 4.1 它是一张“可流程化任务”的菜单

你会看到很多原本只靠经验临场做的任务——需求澄清、研究大纲、风格选择、文章终修、架构治理、会话复盘——都可以被写成有输入、有步骤、有停点、有验收的能力包。

### 4.2 它是一套 Skill 设计样本，而不只是安装清单

最值得复制的是结构：

- Karpathy 四原则的短底线；
- Waza 的单触发、单结束条件；
- 营销技能的共享上下文底座；
- 29+1 的单路由策略；
- 电商视觉文案的人工确认门；
- 深度研究的 JSON 中间产物；
- HyperFrames 的确定性渲染；
- Skill Doctor 的失败证据驱动改进。

### 4.3 它帮助你区分“方法缺口”和“工具缺口”

如果 Agent 不知道怎样做，需要 Skill；如果知道怎样做但碰不到系统，需要 CLI/MCP；如果每次风格漂移，需要模板或设计系统；如果总说完成但无法证明，需要测试和质量门。诊断错类型，就会不断堆提示词却没有效果。

### 4.4 它可以成为你自己的能力库数据源

可以把候选条目转成内部清单：任务、形态、依赖、权限、输入、输出、验证、负责人、版本、试验结果。你最终拥有的不是一堆外部链接，而是一张知道“何时用什么、是否真的有效”的私人能力图谱。

### 4.5 它提示你把复盘也做成能力

大多数人只收藏生成型 Skill，长期差异却来自评测和改进。Skill Doctor 代表了更重要的一层：从真实会话找证据，判断 Agent 为什么慢、为什么返工、哪条 Skill 没触发，再做小修改。

## 5. 推荐给你的最小起步栈

不建议一次安装。先用思想和结构建立五个槽位：

| 槽位 | 初始选择 | 你得到什么 | 首个试验 |
| --- | --- | --- | --- |
| 目标 | `/goal` 模式 | 结果、边界、验证、暂停条件 | 为一个两小时以上任务写目标契约 |
| 研究 | 大纲先行模式 | 可增量的中间产物与来源分离 | 用同一主题比较“边搜边写”和“大纲→检索→报告” |
| 执行 | 一个小型工程/文档 Skill | 稳定步骤与明确结束条件 | 只选一个高频重复任务试用 |
| 验证 | 一张任务专用检查表或确定性测试 | 可观察的完成标准 | 比较返工次数、测试结果与人工修改时间 |
| 改进 | Skill Doctor 思路 | 从失败证据修改能力 | 每 5～10 次真实任务复盘一次，而非凭感觉改 Prompt |

只有当某个槽位被真实任务证明需要外部动作时，再添加 CLI 或 MCP。

## 6. 采用一个模块的四步实验

### 第一步：写基线

记录没有该能力时的完成率、补充说明次数、测试通过率、人工修改时间、总耗时和无关改动。

### 第二步：审查能力包

确认触发、输入、输出、脚本、网络、凭据、写入范围、许可证、失败和卸载方式。

### 第三步：只做一个真实 A/B 任务

对同一个任务使用相同输入和环境。不要同时换模型、换工具、换模板，否则无法判断效果来自哪里。

### 第四步：保留最小有效机制

如果提升来自其中一张检查表，就不必保留整个大型插件；如果只有 CLI 真正有用，可以把方法规则改成自己的；如果没有可测改善，直接移除。

## 7. 可扩展方向：从目录走向能力基础设施

### 方向 1：机器可读能力清单

为每项能力建立统一 manifest：触发、输入、输出、工具、权限、依赖、兼容 Agent、版本、许可证、失败模式和验收方法。

### 方向 2：能力图谱与组合器

用图表示“前置、替代、互补、冲突、产物输入”。用户给出任务后，不是推荐最热门的 Skill，而是生成最小能力链。

### 方向 3：兼容与权限解析

自动判断当前操作系统、Agent、运行时、MCP 服务和账号是否满足前置；安装前显示将读取、写入和联网的范围。

### 方向 4：标准任务评测台

为工程、研究、文档、设计分别建立可复现样例，记录成功率、质量、时间、Token、人工干预和失败类型。Star 只作背景数据。

### 方向 5：安全沙箱与 dry-run

脚本和外部写操作先在受限环境或模拟模式运行，展示计划变更，再由用户批准真实执行。

### 方向 6：团队私有能力库

把公共方案 fork 成内部版本，增加负责人、适用项目、数据分级、审批、版本、弃用和回滚策略。

### 方向 7：会话到 Skill 的反馈闭环

定期抽样真实任务，识别未触发、误触发、步骤冗余、工具失败和验收缺失，自动生成小型修改提案，但由人决定是否合并。

## 8. 最终判断

Atlasnote 对你最重要的意义，不是“这里有 81 个东西可以装”，而是它展示了一套更成熟的 Agent 观：

> 能力不是一段神奇提示词，而是目标、上下文、程序、工具、约束、验证和反馈的组合。

一旦按这个视角看，你就不会再问“哪个 Skill 最强”，而会问：“我的工作链现在缺哪个角色？用最小的什么机制，能让结果变得可执行、可验证、可积累？”
