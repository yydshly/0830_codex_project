# 01｜FDE 概念与岗位边界

## 1. 什么是 Forward Deployed Engineer

Forward Deployed Engineer 常译为“前线部署工程师”“客户现场工程师”或“前向部署工程师”。这些译法容易让人误以为它只是安装和运维角色。更准确的理解是：

> FDE 是进入关键客户工作环境，和客户共同发现问题、编写生产代码、集成真实系统、控制风险并推动采用的产品型工程师。

“Forward”表示工程能力向客户一线前移，“Deployed”既指人深入客户现场，也指把系统真正部署到生产。

Anthropic 当前职位说明给出的任务包括：

- 与战略客户协作，推动 AI 应用落地；
- 在客户系统中使用 Claude 构建生产应用；
- 交付 MCP Server、子 Agent 和 Agent Skills；
- 为企业部署提供高接触度支持；
- 识别并固化可复用部署模式，反馈给产品和工程团队；
- 在部分地点前往客户现场工作。

来源：[Anthropic — Forward Deployed Engineer](https://job-boards.greenhouse.io/anthropic/jobs/5302966008)，访问于 2026-08-30。

## 2. 为什么需要 FDE

通用模型和企业价值之间存在一段“最后一公里”，但这段路通常比最后一公里更复杂：

| 通用模型已经具备 | 客户生产环境仍然缺少 |
| --- | --- |
| 语言理解与生成 | 可验证的业务成功指标 |
| 推理和规划 | 真实数据、身份、权限和工具 |
| 工具调用能力 | 合理的工具边界和失败处理 |
| 长上下文 | 相关、及时、合规的上下文选择 |
| 通用知识 | 行业流程、内部政策和组织共识 |
| 一次性优秀回答 | 多次运行的一致性和可运营性 |

客户很少能一开始就给出完整需求。他们更常说“我们想用 AI 提高效率”，但不知道哪个环节值得做、能让 Agent 做到哪一步、谁承担错误、如何通过安全审核。FDE 的作用就是把模糊愿望转成一个有边界、可测量、可上线的系统。

## 3. FDE 的完整工作循环

### 阶段 A：发现

目标是找到真实工作，而不是收集功能愿望。

- 谁在执行任务？
- 输入和产出分别是什么？
- 当前流程中最耗时、最容易错的步骤是什么？
- 哪个系统是事实来源？
- 错误的经济、合规和声誉成本多大？
- 用户真正愿意改变哪一步？

### 阶段 B：界定

把问题变成可交付范围：

- 选择一个高频、可观察、失败可控的初始工作流；
- 定义准确率、完成时间、升级率、采用率、成本等指标；
- 明确只读、生成草稿、经审批写入和自动执行的权限等级；
- 确认数据边界、部署环境和安全评审要求。

### 阶段 C：构建

FDE 不是把设计文档交给另一支工程团队，而是亲自实现关键路径：

- Claude API 或 Agent SDK 调用；
- 工具/MCP 接口；
- 检索和上下文装配；
- 身份、权限、验证、重试和审计；
- 测试、Evals、可观测性和人工审批。

### 阶段 D：验证与上线

- 用历史真实案例建立初始 Evals；
- 在隔离环境和小用户组中运行；
- 同时检查输出、工具轨迹和最终系统状态；
- 设定上线门槛、暂停条件和回滚机制；
- 观察真实用户是否采用，而不只看离线准确率。

### 阶段 E：扩展与产品反馈

一次性定制不是最终目标。FDE 要识别：

- 哪些连接器可以复用；
- 哪些工具设计适用于多个客户；
- 哪些安全控制应成为平台能力；
- 哪些模型失败是产品或研究团队需要解决的共性问题；
- 哪些交付步骤可以模板化。

## 4. 与相邻角色的区别

边界并非绝对，不同公司会使用不同职位名称。下面比较的是典型重心。

| 角色 | 主要优化目标 | 是否长期写生产代码 | 是否承担客户发现 | 是否进入客户环境 | 是否反馈产品模式 |
| --- | --- | --- | --- | --- | --- |
| 软件工程师（SWE） | 产品与平台质量 | 高 | 通常较少 | 通常较少 | 有，但多来自产品内部 |
| 机器学习工程师（MLE） | 模型/数据/训练与推理系统 | 高 | 视岗位而定 | 较少 | 以模型系统为主 |
| Applied AI Engineer | AI 应用质量和通用能力 | 高 | 中等 | 中等 | 高 |
| Solutions Architect | 方案可行性、架构与采用 | 中低到中 | 高 | 高 | 中高 |
| 技术顾问/专业服务 | 项目成功与客户满意度 | 视合同而定 | 高 | 高 | 中等 |
| FDE | 客户业务结果、生产落地与可复用模式 | 高 | 高 | 高 | 高 |

区分 FDE 的最好问题不是“会不会见客户”，而是：这个人是否能从发现一直负责到生产结果，并亲自跨越业务与代码之间的断层？

## 5. Anthropic FDE 的能力模型

### 5.1 生产工程

- Python 为核心，最好还掌握 TypeScript、Java 等企业常用语言；
- API、JSON、异步、分页、限流、重试、超时；
- 数据验证、单元测试、幂等操作、错误模型；
- 身份、权限、Secrets、审计与可观测性；
- 能在陌生代码库和受限企业环境中调试。

### 5.2 Agent 系统

- 区分单次模型调用、固定 Workflow 和自主 Agent；
- Prompt 与上下文工程；
- Tool Use、MCP、结构化输出；
- Agent Skills、子 Agent 和状态管理；
- 检索、长上下文、成本/延迟管理；
- 轨迹分析、失败恢复和停止条件。

### 5.3 评测与安全

- 先定义成功，再设计 Evals；
- 同时验证结果、轨迹和环境最终状态；
- 组合确定性、模型和人工评分器；
- 最小权限、数据最小化、人工审批、沙箱和回滚；
- 识别幻觉、Prompt Injection、越权、隐私泄漏与滥用风险。

### 5.4 客户与业务判断

- 发现客户真正的流程和约束；
- 在业务负责人、工程、安全、法务和操作人员之间对齐；
- 把模糊目标变成范围、指标和阶段性门槛；
- 在“快速看到价值”和“不过早扩大风险”之间做取舍。

### 5.5 高主动性与低自我

“高主动性”不是未经授权地做更多，而是在既定范围内主动搜集证据、解决障碍并闭环；“低自我”不是没有技术判断，而是能够让事实、客户目标和安全要求高于个人方案偏好。

## 6. FDE 如何衡量成功

代码提交数和 Demo 效果都不足以单独衡量 FDE。更完整的指标包括：

| 维度 | 示例指标 |
| --- | --- |
| 业务 | 处理时间、完成率、节省成本、收入、积压减少 |
| 质量 | 正确率、引用准确率、升级准确率、用户修订量 |
| 可靠性 | 工具成功率、端到端成功率、重复运行一致性、故障率 |
| 安全 | 越权率、敏感数据暴露、危险动作阻断率、审计完整性 |
| 运营 | 延迟、单任务成本、告警质量、恢复时间 |
| 采用 | 活跃用户、留存、流程覆盖率、用户信任 |
| 复用 | 可复用连接器、Skills、Evals、部署模板和产品反馈数量 |

## 7. 什么样的人适合 FDE

较强匹配通常表现为：

- 喜欢写代码，也愿意反复理解客户真实工作；
- 能在需求不完整时推进，但会明确假设和风险；
- 对“系统是否被使用”比“架构是否漂亮”更敏感；
- 能和高管谈价值，也能和工程师一起读日志；
- 接受一定的现场工作和上下文切换；
- 对隐私、安全和可靠性有工程化意识。

可能不匹配的信号：

- 只想研究模型，不愿处理集成、权限和组织问题；
- 只想做售前演示，不愿承担生产代码和上线后的问题；
- 只接受完全明确的需求；
- 倾向于用更多框架和 Agent 掩盖尚未理解的业务流程；
- 不喜欢频繁沟通、客户现场或跨职能冲突。

## 8. 本研究的岗位定义

后续文档统一使用下面的工作定义：

> Anthropic FDE 是 Applied AI 团队中的客户嵌入式生产工程角色：以安全可靠的 Claude 应用解决战略客户的真实业务问题，同时把现场经验转成可复用的产品、工程和部署模式。

这个定义有官方职位说明支持；至于具体面试轮次、题型顺序和不同团队权重，则不能从官方职位说明直接得出。
