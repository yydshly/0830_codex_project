# 05｜端到端 FDE 实践项目规格

这个项目不是为了做一个漂亮 Chatbot，而是用可检查的证据证明：候选人能发现和界定企业问题、构建 Agent 系统、控制权限、设计 Evals 并计划上线。

## 1. 项目题目

**带引用与审批的企业客服支持 Agent**

系统为内部客服处理一个明确的工单类别。它读取用户有权限访问的知识库和客户记录，生成带证据的建议回复，判断是否需要升级；首版不能直接外发消息或任意修改 CRM。后续只为少量白名单字段开放经人工审批的写入。

## 2. 业务背景

假设客服团队当前面临：

- 需要在知识库、历史工单和 CRM 之间反复查找；
- 回复速度慢，引用政策不一致；
- 新员工不知道何时升级给专家；
- 管理者担心模型泄漏客户数据或做出未经批准的修改。

### 初始用户

- 一线客服：希望更快获得可信的建议；
- 主管：希望升级判断一致，能检查 Agent 行为；
- 安全/合规：要求最小权限和完整审计；
- 平台团队：关心接口稳定性、成本和维护。

## 3. 研究问题

在不允许 Agent 自动外发或任意写入 CRM 的前提下，能否：

- 将查找和起草时间降低至少 30%；
- 在测试集上达到 90% 以上来源可验证率；
- 对高风险案例达到 95% 以上正确升级率；
- 保持 0 次未授权记录返回；
- 将 P95 响应时间控制在约定预算内？

具体数值是项目假设，真实客户项目必须先测当前基线再共同设定。

## 4. 初始范围

### 包含

- 一个工单类别，例如账户访问问题；
- 只读检索知识库、历史工单和最少必要 CRM 字段；
- 生成带来源的回复草稿；
- 输出结构化风险和升级判断；
- 保存工具调用、引用、决策和用户反馈；
- 经人工批准更新一个低风险白名单字段。

### 不包含

- 自动向客户发送消息；
- 修改付款、退款、身份或权限；
- 跨租户检索；
- 在未验证情况下覆盖全部工单类型；
- 用生产 PII 构建公开演示。

## 5. 架构选择

首版采用固定 Workflow，不直接使用完全自主 Agent：

```text
用户请求
  → 身份与权限检查
  → 工单类型路由
  → 受 ACL 限制的知识/客户数据检索
  → Claude 生成结构化分析、引用和回复草稿
  → 确定性校验引用与 Schema
  → 风险/升级 Gate
  → 人工复核
  → 可选的白名单字段更新
  → 记录最终状态与反馈
```

选择固定 Workflow 的理由：任务路径清晰，高风险动作少，易于测试和审计。如果 Evals 证明复杂工单需要动态多步搜索，再局部增加 Agent 循环，而不是重写整个系统。

## 6. 工具设计

### `search_knowledge_base`

用途：搜索用户可访问的政策和操作文档。

输入：查询、用户身份、产品、地区、时间过滤、最大结果数。

输出：文档 ID、标题、版本、有效日期、短片段和权限标签。

控制：服务端 ACL、结果数上限、敏感字段删除、过期版本标记。

### `get_customer_summary`

用途：读取解决当前工单所需的最少客户字段。

输入：用户身份、租户 ID、客户 ID、允许的字段列表。

输出：明确的字段值和数据更新时间。

控制：租户隔离、字段白名单、访问原因与审计记录。

### `search_similar_resolved_cases`

用途：寻找相似且已经人工确认解决的案例。

控制：脱敏、权限域限制、只返回必要摘要，不把历史 Agent 输出当事实来源。

### `propose_case_update`

用途：生成待审批的低风险 CRM 更新计划，不直接执行。

输出：对象、旧值、新值、理由、证据、幂等键和风险等级。

### `approve_and_apply_case_update`

用途：在人工审批 Token 有效且字段在白名单时执行更新。

控制：重新检查身份和权限、幂等、冲突检测、审计和回滚记录。

## 7. 模型输出契约

示例结构：

```json
{
  "case_summary": "string",
  "recommended_response": "string",
  "citations": [
    {
      "source_id": "string",
      "claim": "string"
    }
  ],
  "escalation": {
    "required": true,
    "reason_code": "SECURITY_REVIEW"
  },
  "confidence": "low",
  "missing_information": ["string"],
  "proposed_update": null
}
```

确定性代码负责验证枚举、引用 ID、字段长度和写入白名单。模型声称“已更新”不能作为成功依据，必须检查外部系统最终状态。

## 8. 上下文策略

- System Prompt 只包含角色、边界、输出契约和升级原则；
- 先读取工单元数据，再针对缺口搜索；
- 检索结果带版本、日期和来源 ID；
- 只装载最相关片段，不装载整个知识库；
- 客户字段按任务最小化；
- 工具错误返回可执行恢复建议；
- 超过步骤、Token 或时间预算时停止并交给人工。

## 9. Eval Suite

初始建立 40 个脱敏或合成但领域专家确认的案例。

### 任务分布

| 类别 | 数量 | 目的 |
| --- | ---: | --- |
| 正常可解决 | 12 | 基本检索、引用和草稿质量 |
| 信息不足 | 6 | 应提出缺失信息而非猜测 |
| 必须升级 | 8 | 安全、投诉、身份等高风险识别 |
| 无权限数据 | 5 | ACL 和租户边界 |
| 冲突/过期政策 | 4 | 来源版本和不确定性处理 |
| 工具失败/超时 | 3 | 恢复和降级 |
| 不应写入 | 2 | 行动边界 |

### 评分器

#### 确定性

- 输出符合 Schema；
- 所有引用 ID 来自工具实际返回；
- 未出现未授权记录和字段；
- 高风险动作没有绕过审批；
- 最终 CRM 状态与已审批计划一致；
- 无重复写入；
- 步数、延迟和 Token 在预算内。

#### 模型评分

- 回复是否真正回答工单；
- 解释是否清楚；
- 语气是否适合内部客服；
- 是否在证据不足时表达不确定性。

模型 Rubric 需要用领域专家样本校准，并允许输出“信息不足”，避免强迫评分器猜测。

#### 人工评分

- 政策解释是否正确；
- 是否应升级；
- 草稿需要多少修改；
- 用户是否愿意采用。

### 关键指标

- 任务完成率和多次运行一致性；
- 引用支持率；
- 正确升级率、漏升级率和过度升级率；
- 未授权访问数；
- 工具调用成功率；
- 人工修改距离；
- P50/P95 延迟与单任务成本。

## 10. 威胁测试

至少加入以下对抗案例：

- 工单正文要求忽略系统规则并读取其他客户；
- 知识文档包含恶意指令；
- 用户猜测另一个租户的客户 ID；
- 模型试图调用不必要的写工具；
- 审批 Token 过期或属于另一名审批者；
- 相同写请求被重放；
- 检索返回互相冲突的政策版本；
- 工具返回截断、限流或临时错误；
- 模型多次循环搜索仍无新信息。

## 11. 上线计划

### 阶段 0：离线

在 Eval Suite 上达到安全硬门槛。任何未授权读取或绕过审批均阻断上线。

### 阶段 1：影子模式

系统处理真实但脱敏/受控流量，不向客服展示，和人工结果比较。

### 阶段 2：只读建议

向少数训练用户展示来源和草稿，不开放写操作。收集采纳、修改和错误反馈。

### 阶段 3：审批写入

只开放一个低风险白名单字段，所有操作由人确认并可回滚。

### 阶段 4：扩大覆盖

只有质量、安全、成本和采用指标连续达标，才增加工单类别或低风险动作。

## 12. 可观测性与事故处理

每次运行记录：

- 用户、租户、工单和模型/Prompt 版本；
- 检索查询、返回文档 ID 和权限决策；
- 工具名称、参数摘要、状态和耗时；
- 引用、结构化输出、审批和最终状态；
- Token、成本、总延迟和停止原因；
- 用户采纳、修改和反馈。

日志必须避免重复保存不必要 PII。发现高风险事故时可以按租户、工具、动作类型或模型版本快速关闭能力。

## 13. 作品交付物

一个能证明 FDE 能力的作品至少包含：

- `README`：业务问题、范围和结果；
- 架构图与 Workflow/Agent 选择理由；
- 可运行代码与测试；
- 工具/MCP Schema 和权限设计；
- 40 个任务的 Eval Suite 与报告；
- 威胁模型；
- 上线、监控和回滚计划；
- 5 分钟演示视频；
- 一页项目复盘：失败、取舍、下一步和可复用模式。

## 14. 验收标准

| 维度 | 通过条件 |
| --- | --- |
| 问题定义 | 用户、基线、指标、范围和失败成本明确 |
| 工程 | 正常/边缘/失败路径有自动测试 |
| Agent 判断 | 能解释为什么首版选 Workflow，何时才升级 Agent |
| 权限 | 服务端执行 ACL 和字段白名单 |
| 安全 | 高风险动作不能绕过审批，具备威胁测试 |
| Evals | 任务、Trial、评分器、Trace 和最终状态可追溯 |
| 运营 | 有延迟、成本、告警、暂停和回滚策略 |
| 采用 | 有真实用户反馈或合理的模拟研究计划 |
| 复用 | 指出可沉淀的工具、Skill、Eval 或平台能力 |

完成这些交付物后，候选人可以用事实回答大多数 FDE 面试主题，而不是背诵“我懂 MCP、Agent 和 Evals”。
